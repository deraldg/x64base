## Purpose

DD-021 answers the question: how does the data-dictionary work become part of the project without becoming a one-time audit dump?

The design target is a repeatable redocumentation system:

```text
code/scripts/HELP/schemas/rules/runtime behavior change
  -> rescan
  -> regenerate manifests
  -> parse proof where needed
  -> reconcile evidence
  -> stage candidate facts
  -> validate staging package
  -> triage review queue
  -> promote only through explicit gates
  -> regenerate documentation only through explicit gates
```

DD-021 does not install files into the repo. It proposes the placement model and the run-cycle contract.

## Key decision

The data dictionary should be integrated as a durable redocumentation lane, not as a one-time report.

That means the repo needs stable homes for:

- reusable Python 3.12 tools;
- versioned JSON schemas;
- human-readable specs;
- per-run manifests;
- per-run reports;
- candidate staging packages;
- review queues;
- run history and hashes;
- guarded promotion records;
- documentation regeneration records.

## Proposed top-level placement

```text
tools/datadict/
  reusable Python 3.12 tools after review

docs/datadict/
  specs/
  schemas/
  reports/<run_id>/
  manifests/<run_id>/
  staging/<run_id>/
  review_queue/
  runlog/
  templates/

dottalkpp/scripts/datadict/
  reviewed DotScript / capture templates needed by DotTalk++ runtime or maintenance

dottalkpp/data/metadata/datadict/
  future promoted/staged x64base catalog DBFs, only after explicit authorization
```

## Important boundary

The default lane remains report-only. DD-021 does not create DBFs, import rows, rewrite HELP, run CMDHELPCHK, run DotTalk++, build C++, or mutate source.

Future catalog promotion requires a separate explicit gate such as:

```text
EXPLICIT_PROMOTION_AUTHORIZED
```

Future documentation rebuilds require a separate explicit gate such as:

```text
DOC_REGEN_AUTHORIZED
```

Future HELP DATA mutation requires a separate explicit gate such as:

```text
HELP_MUTATION_AUTHORIZED
```

## What gets checked in?

DD-021 recommends committing stable contracts and reviewed summaries, but not every local generated artifact.

Generally checked in:

- stable tools after review;
- JSON schemas;
- specs and doctrine;
- accepted run summaries;
- hash manifests for accepted runs;
- review queues and dispositions when they are part of project work.

Usually not checked in by default:

- bulky local manifests from every run;
- local transcript captures;
- temporary staging directories;
- runtime DBF/CDX/DBT catalog products;
- cache/scratch output.

## Redocumentation run object model

DD-021 adds the following planned catalog concepts:

```text
DD_RUN
DD_RUN_ARTIFACT
DD_RUN_GATE
DD_RUN_DIFF
DD_REVIEW_DISPOSITION
DD_PROMOTION_EVENT
DD_DOC_REGEN_EVENT
```

These are not final x64base tables yet. They are the run-history concepts needed for repeatability.

## Why this matters

A new command, field, table, rule, script, HELP topic, or runtime behavior should become visible in the next redocumentation run.

The system should report:

- new object detected;
- source contract missing;
- HELP link missing;
- runtime proof missing;
- profile boundary unclear;
- staging package invalid;
- review disposition required;
- ready for guarded promotion.

That keeps the data dictionary alive as the codebase grows.
