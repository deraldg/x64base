<p><strong>UIDEF is UI DEFINITION</strong> -- a user-interface definition stored as an
x64base DBF design table with a memo sidecar. Not identity, not accounts,
not BBS. The acronym went unexpanded on every page that used it until
2026-09-03.</p>
<p><strong>Alpha -- chartered and in progress.</strong> AIF-120 is no longer a planned lane
waiting to start. The design-table contract, importers, validators, generators
and four target backends exist in development. Every lane ruling remains
review-needed until the maintainer accepts it.</p>
</blockquote>
<h2 id="what-the-lane-is-for"><a class="no-underline" href="#what-the-lane-is-for">What the lane is for</a></h2>
<p><strong>Traditional menus and forms as the interface to GUI generation and adaptation
-- as a builder, or as an API.</strong></p>
<p>Decades of application interfaces already exist as screen, menu and class
definitions. The lane treats them as INPUT rather than as history: read an
existing design into a portable table, then emit it against a toolkit chosen
now. That is the ADAPTATION half. The GENERATION half is the same path with a
new document at the front, authored by a tool or by hand.</p>
<p><strong>The four backends are instruments, not products</strong>, and that is why none of
them is a rich application. Each one exists to answer a different question about
the same document: whether it survives a second toolkit (Tk), whether it
survives having no pixels at all (character cell), whether it reaches a browser
(HTML), and whether it reaches the engine for real (wxWidgets). A backend that
made things pretty would be worse at that job. The lane's own success test says
so: a successful render by one toolkit is not enough, and a target that cannot
honour something the document says must report the loss <strong>by name</strong>.</p>
<h2 id="the-vocabulary-sketch-that-came-first"><a class="no-underline" href="#the-vocabulary-sketch-that-came-first">The vocabulary sketch that came first</a></h2>
<p>The original website seed proposed commands such as <code>CREATE WINDOW</code>, <code>CREATE MENU</code>, <code>DEFINE BUTTON</code>, and <code>ON CLICK</code>. That was a useful vocabulary sketch, but
it put the syntax before the portable object.</p>
<p>The lane's actual deliverable is a <strong>UI definition table</strong>: a DBF document with
a memo sidecar. A future text DSL can author that table, but generators do not
need to parse the text language. They consume the documented table directly.</p>
<h2 id="why-the-interface-is-a-database-table"><a class="no-underline" href="#why-the-interface-is-a-database-table">Why the interface is a database table</a></h2>
<p>FoxPro screen, menu, class, and report designers stored their definitions in
DBF-shaped files. That prior art fits x64base unusually well: the engine can
open, browse, validate, index, transform, and transport its own application
definitions.</p>
<p>The result is an interchange format rather than a toolkit wrapper:</p>
<pre><code class="language-text">future DSL text or a visual designer
                |
                v
       UIDEF design table (DBF + memo)
                |
                +--> manifest and refusal report
                +--> wxWidgets C++ generator
                +--> Tk renderer
                +--> HTML renderer
                +--> character-cell renderer
</code></pre>
<p>The rule shared by every target is simple: if a backend cannot honor something
the document says, it reports the loss by name. Silent degradation is the
defect.</p>
<h2 id="the-design-table"><a class="no-underline" href="#the-design-table">The design table</a></h2>
<p>The current contract uses three record kinds: <code>DOC</code>, <code>FONT</code>, and <code>OBJ</code>. Its
fields carry identity, parentage, layout order, tab order, span, kind, flow,
data binding, font reference, provenance, properties, original coordinates,
handlers, data sources, and notes.</p>
<p>The object vocabulary covers ordinary controls and application structure:</p>
<pre><code class="language-text">form panel group pageset page splitter
label text button check radio list combo image menu
grid tree detail summary statusbar
</code></pre>
<p>Geometry is expressed as <strong>layout intent</strong>. <code>FLOW</code>, <code>ORDINAL</code>, <code>Weight</code>, and
<code>Fill</code> describe containment and allocation. Imported absolute coordinates stay
in <code>ORIGIN</code>, with their units, instead of pretending a pixel and a character
cell mean the same thing.</p>
<h2 id="what-exists-now"><a class="no-underline" href="#what-exists-now">What exists now</a></h2>
<h3 id="import-and-authoring"><a class="no-underline" href="#import-and-authoring">Import and authoring</a></h3>
<ul>
<li>Authoring tools produce UIDEF DBF/FPT documents and reproducible acceptance
and refusal fixtures.</li>
<li>Importers read FoxPro <code>.SCX</code>, <code>.VCX</code>, and <code>.MNX</code> design tables.</li>
<li>Class, implied-child, font, encoding, menu-nesting, binding, and layout rules
have explicit contracts rather than being inferred independently by each
renderer.</li>
</ul>
<h3 id="validation-before-rendering"><a class="no-underline" href="#validation-before-rendering">Validation before rendering</a></h3>
<p>The manifest reads what a document requires and compares it with a target's
declared abilities. Unknown properties, invalid bindings, unresolved sources,
unsupported layout, and target-specific losses are reported before a window is
presented as successful.</p>
<h3 id="four-backend-views"><a class="no-underline" href="#four-backend-views">Four backend views</a></h3>

























<table><thead><tr><th>Target</th><th>Current development role</th></tr></thead><tbody><tr><td>wxWidgets</td><td>Generates compiled C++ windows and connects to the native runtime.</td></tr><tr><td>Tk</td><td>Independent graphical implementation used to test portability and threading rules.</td></tr><tr><td>HTML</td><td>Browser-oriented projection of the same design document.</td></tr><tr><td>Character cell</td><td>Text rendering that makes geometry loss and cell allocation explicit.</td></tr></tbody></table>
<p>The <code>splitter</code> is a useful portability example. wxWidgets has a native sash;
Tk and HTML preserve different subsets of its constraints; the character-cell
backend derives a fixed separator. The document carries the full intent, and
each target states what it cannot preserve.</p>
<h3 id="engine-integration"><a class="no-underline" href="#engine-integration">Engine integration</a></h3>
<p>Generated wx frontends can open the tables named by their own UIDEF document,
resolve location through a workspace, bind grids to the engine's tuple stream,
and use the engine's typed locking services. The UIDEF document is also a CMake
input: author the document, generate C++ from it, compile it, and link it
against the engine, all from <code>cmake --build</code>.</p>
<p><strong>That target is standalone on purpose and is not reached by the root build.</strong>
Configuring the root build to produce one window would also build the whole
shell, so the lane follows the pydottalk precedent (AIF-119) instead. The
consequence worth knowing: a normal build never compiles this lane, so it
will not appear in a build log.</p>
<p><code>APPGUI</code> and its alias <code>GUI</code> launch DotTalk++ Workbench through the product's
registered GUI path. That proves a shell-to-window launcher, but it is not a
UI-DSL command and should not be confused with <code>CREATE WINDOW</code> being live.</p>
<p><a href="/images/evidence/dottalk-appgui-launcher-process-boundary-20260826.png"><img src="/images/evidence/dottalk-appgui-launcher-process-boundary-20260826.png" alt="The DotTalk++ CLI and the Workbench side by side: appgui typed at the prompt launches dottalk_wb.exe, and the CLI then reports zero open work areas while the Workbench beside it holds thirteen"></a></p>
<p><em>The launcher, and the limit of what it proves, in one frame (2026-08-26).
<code>appgui</code> prints the path of the executable it starts and starts it. What the
same frame shows is that this is all it did: the shell that launched the window
reports <code>0 area(s) open</code> immediately afterwards, while the window holds thirteen
areas of its own. A process was started. No interface was described, generated
or bound -- which is the distance between <code>APPGUI</code> and <code>CREATE WINDOW</code>.
Unrelated desktop windows are masked.</em></p>
<h2 id="relationship-to-workbench"><a class="no-underline" href="#relationship-to-workbench">Relationship to Workbench</a></h2>
<p>DotTalk++ Workbench is the project's first-party database application. UIDEF is
the description and generation contract for application interfaces, including
frontends the project does not own.</p>
<p>Workbench is therefore evidence and a demanding design specimen, not the only
target. The lane has already described the Workbench frame as a UIDEF document
and generated a recognizable wx structure back from it. That round trip exposed
missing proportional-layout vocabulary, which was then added without changing
older documents.</p>

<h2 id="known-alpha-boundaries"><a class="no-underline" href="#known-alpha-boundaries">Known Alpha boundaries</a></h2>
<ul>
<li>The user-facing text DSL has not been implemented. The design table is the
current authoring and interchange contract.</li>
<li><code>menu</code> still lacks the same depth of first-class proof as the other kinds.</li>
<li>Data frames need fuller paging and refresh behavior as the cursor moves.</li>
<li>Nested splitter teardown is proven on Tk, but a wxWidgets lifetime probe
currently exposes a fatal teardown defect. Layout proof does not erase that
limitation.</li>
<li>Windows/MSVC support must be established by a current native build before it
is promoted as proven here.</li>
<li>Some engine naming and workspace behavior is being hardened alongside the
multi-workspace work; UIDEF must consume those shared services rather than
grow private alternatives.</li>
</ul>
<h2 id="proof-and-publication-gates"><a class="no-underline" href="#proof-and-publication-gates">Proof and publication gates</a></h2>
<p>The lane advances when the same document remains intelligible across targets,
losses are explicit, generated frontends use the real engine, and the source
contracts feed HELP, SelfDoc, manuals, and this website. A successful render by
one toolkit is not enough.</p>
