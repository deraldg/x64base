1c:T2cdf,<h2 id="core-rule"><a class="no-underline" href="#core-rule">Core rule</a></h2>
<p><code>implementation checkout</code> is the implementation truth.</p>
<p><code>website source tree</code> is the public publication surface.</p>
<p>The site should present reviewed, provenance-aware derivatives of the runtime,
contracts, HELP, metadata, manuals, and diagrams. It should not invent
technical truth on its own.</p>
<h2 id="full-stack-documentation-push-pass-4"><a class="no-underline" href="#full-stack-documentation-push-pass-4">Full-stack documentation push (pass 4)</a></h2>
<p>The concepts on this page are unchanged. What has evolved is the cadence: a
documentation change now travels the whole stack end to end, and we are on the
fourth full-stack documentation push (pass 4). The data-flow below is the
start-to-finish path a change follows, from implementation evidence to the
public consumers.</p>
<p><a href="/images/sdlc/selfdoc-full-stack-docpush-dfd-v1.svg"><img src="/images/sdlc/selfdoc-full-stack-docpush-dfd-v1.svg" alt="Start-to-finish data-flow of the full-stack documentation push: engine source and registration, HELP, metadata, and inline contracts through SelfDoc/CMDHELPCHK validation, the metacollect harvest exporter, and manualgen/MDO, into doc candidates gated by the public-content guard and the diagram-integrity check, then Phase 9 owner signoff into the manual, the website, and the GPTbase consumers"></a></p>
<details>
<summary>The pass in detail (steps collapsed to reduce clutter)</summary>
<ol>
<li>Produce -- in the implementation checkout: command/function registration, HELP text, metadata, inline contracts, comments, and canaries.</li>
<li>Validate -- SelfDoc / CMDHELPCHK confirm HELP, metadata, and contracts agree with the runtime.</li>
<li>Harvest -- metacollect and the harvest exporter pull reviewed evidence out of the tree.</li>
<li>Generate -- manualgen / MDO assemble manual sections and attach reviewed diagrams.</li>
<li>Gate -- doc candidates must clear the public-content guard and the diagram-integrity check (<code>check:diagrams</code>) before promotion.</li>
<li>Sign off -- Phase 9 owner review: stale-copy audit and generated-page integrity across the site.</li>
<li>Publish -- consumers receive the reviewed derivative: the manual, the website (x64base.com), and the GPTbase bundle.</li>
</ol>
</details>

<h2 id="simplex-and-duplex-gates"><a class="no-underline" href="#simplex-and-duplex-gates">Simplex and duplex gates</a></h2>
<p>The website, manuals, and implementation tree are connected, but they do not
have equal authority.</p>
<p>Rule 1: most technical data on <code>x64base.com</code> must be derived, harvested,
calculated, or reviewed from the implementation checkout. The website may frame
and organize that information, but it should not become the source of runtime,
command, field-format, index, memo, HELP, or manual truth.</p>
<p>Rule 2: the manual may contribute reviewed sections, diagrams, and summaries to
the website. The manual must not consume website copy as technical truth unless
the website artifact is explicitly non-derivable from the implementation tree
and is maintained separately as a public artifact.</p>
<p>Rule 3: <code>README.*</code> files are sacred orientation artifacts. They may be
improved, annotated, or superseded, but a replacement must be versioned so the
older README remains recoverable and comparable. Do not casually overwrite a
README during website, manual, or staging work.</p>
<p>Use these gates:</p>




























































<table><thead><tr><th>Path</th><th>Gate Type</th><th>Rule</th></tr></thead><tbody><tr><td>implementation checkout -> manual</td><td>Simplex default</td><td>Source, HELP, metadata, comments, contracts, canaries, and SelfDoc/manualgen reports feed the manual.</td></tr><tr><td>implementation checkout -> website</td><td>Simplex default</td><td>Website pages should be derivatives of source/runtime/manual evidence, not hand-written replacements for it.</td></tr><tr><td>implementation checkout -> dottalkpp.com lean site</td><td>Simplex default</td><td>Manuals, references, generated docs, downloads, proof packets, and governance should derive from source/runtime/HELP/metadata/SelfDoc/MDO/manualgen evidence.</td></tr><tr><td>manual -> website</td><td>Duplex, reviewed</td><td>Reviewed manual sections may promote into website summaries when proof labels and source anchors remain intact.</td></tr><tr><td>dottalkpp.com lean site -> website</td><td>Duplex, reviewed</td><td>The lean site may contribute selected summary links, route maps, and downloadable artifact notices to x64base.com after review.</td></tr><tr><td>website -> manual</td><td>Blocked by default</td><td>Do not let website prose become manual truth. Only ingest website-owned artifacts that are non-derivable elsewhere.</td></tr><tr><td>website -> dottalkpp.com lean site</td><td>Blocked by default</td><td>Do not let ecosystem prose become technical manual truth unless the artifact is website-owned and non-derivable elsewhere.</td></tr><tr><td>website-owned artifact -> manual</td><td>Exception gate</td><td>Allowed for public-only artifacts such as curated screenshots, branding/UX copy, published contact details, or hosted downloads, when the artifact has an owner and provenance.</td></tr><tr><td>manual -> implementation checkout</td><td>Review gate</td><td>Manual discoveries should become source contracts, TODOs, tests, HELP changes, or SelfDoc tasks before they become runtime claims.</td></tr><tr><td>README replacement</td><td>Versioned artifact gate</td><td>Preserve the prior README version before replacing it; README history is part of project provenance.</td></tr></tbody></table>
<p>If a manual chat wants to "steal" from the website, it should first ask whether
the website text is derivative of the implementation tree. If yes, the manual
should return to the original source/manualgen/SelfDoc evidence. If no, the
manual may cite or ingest the website artifact only after recording why that
artifact is independently maintained.</p>
<h2 id="front-end-naming-rule"><a class="no-underline" href="#front-end-naming-rule">Front-end naming rule</a></h2>
<ul>
<li><code>DotTalk++ Workbench</code> is the family name for front-end/workbench surfaces</li>
<li><code>Parallel GUI/TUI</code> is the public product lane for aligned graphical and terminal interfaces</li>
<li><code>Arctic</code> is the code name for the TUI surface</li>
<li><code>TableTalk</code> is the table-buffering lane, not generic table browsing</li>
<li><code>Foxtalk</code> and fox-derived names remain valid lineage/subsystem names</li>
<li>Classic FoxPro-style syntax may remain for historical and educational reasons</li>
<li>DotTalk++ should not be described as a clone</li>
</ul>
<h2 id="route-bucket-naming-rule"><a class="no-underline" href="#route-bucket-naming-rule">Route-bucket naming rule</a></h2>
<ul>
<li>short route buckets such as <code>/docs/dottalk/*</code> may remain stable for continuity</li>
<li>those route buckets are not the preferred public brand</li>
<li>visible page titles, navigation labels, and prose should use <code>DotTalk++</code></li>
<li>historical names should be explained, not silently promoted into top-level branding</li>
</ul>
<h2 id="educational-goal"><a class="no-underline" href="#educational-goal">Educational goal</a></h2>
<p>The stack is meant to teach full-stack thinking from beginning to end:</p>
<ul>
<li>engine and file/runtime behavior</li>
<li>command shell and automation</li>
<li>HELP, metadata, and contracts</li>
<li>manuals and diagrams</li>
<li>GUI/TUI/front-end work</li>
<li>public website publication</li>
</ul>
