Website Documentation Matrix

Matrix of x64base.com sections, document lanes, data-mining feeds, proof artifacts, and publication status.

This matrix documents how the website is fed by the documentation system. It is not a claim that every page is fully automated today. The current site is a reviewed publication surface with a growing set of repeatable feeds from source, HELP, metadata, SelfDoc, manualgen, diagrams, and runtime proof.

Read this first for website maintenance (entry gate). Reading this matrix and classifying every page you will touch is the first step of the website phase -- the entry half of the matrix gate, paired with the closeout re-audit below. This matrix is itself maintained_current: before editing any page, classify it here (static / maintained / maintained_current / derived / generated / reported) and honor the Direction Gates below. Never hand-edit a generated or derived region -- fix the source and regenerate. Closeout gate: on every full-stack push, once the website is approved, this matrix must be updated and re-audited to match the signed-off site (advance Last audited, reclassify any changed pages, record new diagrams and feeds). The run does not close until the matrix is current -- a stale matrix is a fail-closed condition on the website signoff. Last audited: 2026-08-10 (schema-catalog and AI-history evidence pass. Added the dedicated public /schemas/ catalog and the reported /about/ai-assisted-history evidence record, with the timeline and About index updated. The preceding owner-approved full-stack pass 4 was 2026-08-06. Next scheduled run: Document FullStack push v5).

Matrix Authority: Website Design and Retention

This matrix is not only a page-classification table. It is the authority of record for two website policies: design (how pages are structured and what each must carry) and retention (what must be preserved and how). A design or retention decision that is not reflected here is not yet policy. Both route through the same entry/closeout gate as any other website change: read the matrix before the pass, re-audit it at signoff.

Design authority

  • Page structure follows maintenance class. The class decides how a page may be edited and what it must expose: maintained_current carries a present-state region with as_of_date, evidence state, and next gate; generated / derived regions are produced by their authority and never hand-shaped.
  • Evidence before ornament. Every page must answer the Proofed Site Checklist below. Design may frame and organize evidence; it must not manufacture technical truth or hide the proof level.
  • Diagrams. Conceptual/architectural diagrams are hand-authored maintained and kept in sync; data-carrying diagrams are generated from the harvest (AIF-032). Source and generated image are kept together.
  • Naming and routes. Visible titles, nav labels, and prose use DotTalk++; short route buckets may stay stable for continuity but are not the public brand.
  • New page types, hero/diagram placement conventions, and nav/section changes are design decisions and must be classified and recorded here when adopted.
  • Image assets must be license-clean and watermark-free before publish. A website-owned image is only publishable with a clear license and no stock watermark. Open for the next push (v5): public/images/talk-family/arctic-fox.png (the Arctic mascot) may carry a faint stock watermark -- verify its license and replace it with a clean copy at the same path before or during the v5 flush. Also open for v5: public/images/story/x64base-glass-engine.png (origin-story figure) has embedded number plaques that conflict and read as noise -- photoshop or Firefly them out (content-aware / generative remove; the in-environment image tools cannot do object removal), keeping the same path.

Retention authority

The website preserves history rather than overwriting it. The retention rule for a page or artifact is set by its class and by these gates:

  • maintained_current -- preserve event history. The present-state region is replaceable, but prior events and dates are retained, not erased.
  • reported -- append-only. Measurements and checkpoints are appended with pinned provenance; a new run adds evidence, it does not replace the baseline.
  • README / orientation artifacts -- versioned. Preserve the prior version before replacing it; README history is project provenance.
  • Historical source lineage -- byte-preserved. SHA-256-bound, read-only, private roots omitted; checksums and truth-level labels retained.
  • Diagram sources retained with images. Never discard the .mmd / .drawio source when publishing a generated image.
  • Publication checkpoints -- pinned. Accepted manual/reference snapshots and the commits that served them are recorded and kept recoverable.

Retention is enforced at closeout: the matrix re-audit confirms that nothing which should have been preserved was overwritten during the pass.

Proofed Site Checklist

A website page is proofed when the page can answer four questions:

  1. What source or document lane fed this page?
  2. What proof level is being claimed?
  3. What artifact, command, report, screenshot, or source path backs it?
  4. What needs to be regenerated when the underlying command, function, or lane changes?

The site currently meets this standard best for engine feature crosswalks, data mutators, x64 capacity math, runtime evidence, historical source lineage, and the SelfDoc publication pages. The accepted manual/reference checkpoint is now public in site source; the weaker area remains the fully automated regeneration loop, which is documented as partial rather than complete.
