1d:T395a,<p>This page is the public documentation shelf for the most important document
layers behind x64base, DotTalk++, DotScript, DotTalk++ Workbench, and the
Laboratory Campus.</p>
<p>The website is not meant to be a hand-written brochure. It is a reviewed
publication surface built from the same vertical documentation system used by
the runtime: source comments, usage contracts, HELP, metadata, SelfDoc reports,
MDO organization, manualgen, diagrams, and AI-friendly summaries.</p>
<p>This is the working thesis of the documentation system: x64base should be able
to use its own metadata and documentation infrastructure to describe, validate,
and increasingly prove itself. The website is one reviewed output of that loop,
not the loop itself.</p>
<p><a href="/images/sdlc/important-documents-evidence-spine-v2.svg"><img src="/images/sdlc/important-documents-evidence-spine-v2.svg" alt="Important documents evidence spine showing implementation authority, evidence, SelfDoc collection, MDO review, Manualgen draft validation, the human promotion gate, and reviewed publication"></a></p>
<p>The most important documents are not one flat folder. They move through parallel
lanes: source/runtime proof, HELP explanation, metadata normalization, SelfDoc
review, provenance preservation, and promotion into manuals, diagrams, and the
website.</p>
<h2 id="diagram-attachment-governance"><a class="no-underline" href="#diagram-attachment-governance">Diagram Attachment Governance</a></h2>
<p>The diagram lane now has an explicit attachment map in the implementation tree:</p>
<ul>
<li><code>docs/manuals/developer/manualgen/reports/diagram-publication-attachment-matrix-v1.csv</code></li>
</ul>
<p>That matrix exists so images on the site do not drift into orphan visuals with
no canonical home. Each promoted diagram should answer:</p>
<ol>
<li>Which canonical source asset or Mermaid/Draw.io source owns it?</li>
<li>Which manual chapter consumes it?</li>
<li>Which public page consumes it?</li>
<li>What proof level and review status does it carry?</li>
</ol>
<p>Current promoted site image families already visible here include:</p>
<ul>
<li>SelfDoc / publication SDLC images under <code>public/images/sdlc</code></li>
<li>runtime evidence screenshots under <code>public/images/evidence</code></li>
<li>LabTalk campus/proof diagrams under <code>public/images/labtalk</code></li>
</ul>
<p>The goal is to keep diagrams attached to the same evidence spine as manuals and
command documentation, not to let image assets become a parallel undocumented
truth system.</p>

<h2 id="dottalkppcom----the-lean-entry-site"><a class="no-underline" href="#dottalkppcom----the-lean-entry-site">dottalkpp.com -- The Lean Entry Site</a></h2>
<p>x64base.com is the development and conception site. dottalkpp.com (role updated
2026-08-11, AIF-107) is the lean public entry surface: static HTML, six nav
items, an evidence-tiered status board, changelog instead of news. It is
versioned in <code>deraldg/dottalkpp</code> and deployed through GitHub Pages:</p>
<ul>
<li><a href="/downloads">Releases and reviewed downloads</a></li>
<li><a href="/docs/dottalk/dotscript-language-guide">DotScript guide</a></li>
<li><a href="/docs/dottalk/command-catalog">Command catalog</a></li>
<li><a href="/docs/dev/project-truth">Current project truth</a></li>
</ul>
<p>The separate DotTalk++ artifact domain is not linked publicly while its HTTPS
certificate is unhealthy.</p>
<p>The artifact manifest must carry proof status, review status, and accessibility
status so public links do not outrun the evidence behind them.</p>

command-reference companion contains 183 standalone pages: 164 linked from the

<p>Publication is a checkpoint, not the end of the feed. Later manual updates
should appear here only after they are generated, validated, and reviewed. The
repeatable path remains:</p>
<pre><code class="language-text">source behavior
-> comments and @dottalk.usage / @dottalk.contract headers
-> HELP, CMDHELP, metadata, and comments evidence
-> CMDHELPCHK / SelfDoc validation reports
-> MDO section organization
-> manualgen inventory / validate / dry-run
-> reviewed manual section
-> website manual page or downloadable artifact
</code></pre>
<p>This keeps the public manual honest. If a feature is runtime-evidenced, the
manual can say so. If it is source-evidenced, canary, planned, or
review-needed, the manual should carry that status instead of smoothing it over.</p>
<p>The current follow-up delta is intentionally visible but not over-promoted:
Pinocchio benchmark metadata, comments-audit closeout records, and the full
documentation-run evidence still need a reviewed public-source promotion
before they can become durable public provenance. <code>METACOLLECT-238</code> remains a
separate 238-finding mission rather than an implied part of the completed run.</p>
<h2 id="manual--website-boundary"><a class="no-underline" href="#manual--website-boundary">Manual / Website Boundary</a></h2>
<p>The manual and website can exchange reviewed material, but the direction matters.
The normal flow is simplex: implementation truth feeds SelfDoc/MDO/manualgen,
then reviewed manual sections and website pages. The website should not become
the manual's source of technical truth.</p>
<p>The manual may take from the website only when the target artifact is
website-owned, separately maintained, and not derivable from the implementation
checkout. Examples include curated screenshots, public-only media, navigation
framing, contact details, branding, and hosted-download metadata. For commands,
functions, file formats, engine features, index behavior, table buffering, or
DotScript syntax, the manual must return to source/runtime/HELP/metadata/SelfDoc
evidence instead of copying website prose.</p>
<p><code>README.*</code> files have a stricter preservation rule. They are orientation and
provenance artifacts, not disposable generated output. A README may be improved
or superseded, but if it is replaced the prior version must be preserved as a
versioned artifact so the project history remains auditable.</p>
<h2 id="ai-friendly-documentation"><a class="no-underline" href="#ai-friendly-documentation">AI-Friendly Documentation</a></h2>
<p>AI-friendly documents are useful because the project is broad, but they are not
the source of truth by themselves. They should preserve:</p>
<ul>
<li>source path or report path,</li>
<li>generation date or extraction snapshot,</li>
<li>evidence status,</li>
<li>mutation boundary,</li>
<li>review state,</li>
<li>promotion target.</li>
</ul>
<p>AI-friendly summaries are allowed on the website when they help a reader
navigate the system and when they remain traceable back to source, HELP,
SelfDoc, MDO, or manualgen artifacts.</p>
