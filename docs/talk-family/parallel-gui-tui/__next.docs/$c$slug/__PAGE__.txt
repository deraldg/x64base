6:T199f,<h2 id="what-it-does"><a class="no-underline" href="#what-it-does">What it does</a></h2>
<p>Parallel GUI/TUI is the DotTalk++ Workbench lane that keeps multiple user
interfaces attached to the same engine truth.</p>
<p>The lane exists because x64base is an object-oriented hybrid engine with
several valid front ends: command line, GUI, TUI, browser-facing documentation,
and lab portal surfaces. Those front ends should not drift into separate
stories. They should read from the same command contracts, help metadata,
workspaces, table buffers, relation graphs, tuple output, and runtime evidence.</p>
<h2 id="current-surfaces"><a class="no-underline" href="#current-surfaces">Current Surfaces</a></h2>
<p>Not all of these are the same kind of thing, and the difference matters:</p>
<ul>
<li><strong>DotTalk++ Workbench GUI</strong> -- the real one. A window over the same engine the
CLI drives, reaching the runtime through the command bridge. Alpha, and
screenshot-evidenced on the <a href="/products/parallel-gui-tui">product page</a>.</li>
<li><strong>Arctic TUI</strong> -- a terminal-interface example (see below).</li>
<li><strong>DotTalk++ CLI</strong> -- startup, relation tree, workspace load, tuple-grid output.</li>
<li><strong>Template and demonstration frontends</strong> -- generated or hand-built examples in
C++ and Python that show a surface rather than carry advanced behaviour.</li>
<li><strong>LabTalk Portal and website/manual evidence views.</strong></li>
</ul>
<h2 id="the-workbench-in-the-frames"><a class="no-underline" href="#the-workbench-in-the-frames">The Workbench, in the frames</a></h2>
<p><code>APPGUI</code> (alias <code>GUI</code>) launches the Workbench. These are runtime captures, not
mockups, and they are published including their warnings.</p>
<p><a href="/images/evidence/dottalk-workbench-minidb-memo-hydrated-evidence-20260820.png"><img src="/images/evidence/dottalk-workbench-minidb-memo-hydrated-evidence-20260820.png" alt="DotTalk++ Workbench with thirteen work areas opened from a memo-resident mini-database, every table path resolving under the in-process RAM root"></a></p>
<p><em>Thirteen areas out of one memo field, 2026-08-20. The Path column is the tell:
every table resolves under the RAM root rather than a disk directory.</em></p>
<p><a href="/images/evidence/dottalk-workbench-memo-workspace-browser-evidence-20260820.png"><img src="/images/evidence/dottalk-workbench-memo-workspace-browser-evidence-20260820.png" alt="The memo workspace browser listing saved snapshots with format, stored size and live-or-superseded state, its Open in Workbench button disabled with the reason stated"></a></p>
<p><em>Reading the catalog without hydrating it. The status bar states how many bytes
were read and that nothing was hydrated; the disabled button carries its own
reason.</em></p>
<p><a href="/images/evidence/dottalk-workbench-workspace-open-directory-evidence-20260820.png"><img src="/images/evidence/dottalk-workbench-workspace-open-directory-evidence-20260820.png" alt="Workbench after opening a directory of tables, showing fourteen areas where thirteen tables exist because a backup sidecar was admitted, and a log warning that the active order could not be used"></a></p>
<p><em>Two open defects in one frame -- fourteen areas over thirteen tables because a
table's backup sidecar was admitted as an area, and an order-unavailable
warning. Published as shot rather than reshot.</em></p>
<p><a href="/images/evidence/dottalk-appgui-launcher-process-boundary-20260826.png"><img src="/images/evidence/dottalk-appgui-launcher-process-boundary-20260826.png" alt="The DotTalk++ CLI and the Workbench side by side: appgui typed at the prompt launches dottalk_wb.exe, and the CLI then reports zero open work areas while the Workbench beside it holds thirteen"></a></p>
<p><em>What <code>APPGUI</code> actually does, 2026-08-26. Typing <code>appgui</code> at the <code>.</code> prompt
prints <code>APPGUI: launching ...\bin\dottalk_wb.exe</code> -- the executable it is about
to run -- and starts it as a <strong>separate process</strong>. The proof of that is in the same frame: run
<code>WORKSPACE</code> in the shell straight afterwards and it answers <code>0 area(s) open</code>,
twice, while the Workbench next to it has thirteen areas open on <code>mcc_db</code> with
every path under the RAM root. <code>APPGUI</code> is a launcher, not an in-process mode,
and the two sides do not share state. Unrelated desktop windows are masked.</em></p>
<p><a href="/images/evidence/dottalk-workbench-ram-disk-per-process-defect-20260821.png"><img src="/images/evidence/dottalk-workbench-ram-disk-per-process-defect-20260821.png" alt="Workbench log showing a MINIDB container hydrated into a per-process RAM disk and thirteen areas mirrored, then an APPEND routed to the external CLI failing because that process cannot see the RAM disk"></a></p>
<p><em>The same boundary as a defect, 2026-08-21, and the log explains itself. Loading
<code>cycle_from_ram</code> mounts the RAM disk with the reason attached -- "A RAM disk is
per-process, so the Workbench keeps its own" -- hydrates 15 files and 95,579
bytes out of the memo, and mirrors 13 tables; Browse then shows 200 of 200
STUDENTS rows. Two lines later <code>APPEND</code> is routed to the external CLI, which is
a different process, and it fails with <code>Open failed: DbArea: file does not exist</code>
on the RAM-disk path to <code>STUDENTS.dbf</code>. The table is open in the window and
absent from the process asked to append to it. Published as shot.</em></p>
<p>More frames, including the negative-path inspection and the container rebuild,
are on the <a href="/products/parallel-gui-tui">Parallel GUI/TUI product page</a> and in the
<a href="/docs/labtalk/runtime-evidence">Runtime Evidence Gallery</a>.</p>
<h2 id="boundaries"><a class="no-underline" href="#boundaries">Boundaries</a></h2>
<p>Parallel GUI/TUI is not a separate storage engine. Database semantics remain in
x64base and DotTalk++. Table buffering belongs to TableTalk. Relation traversal
belongs to RelTalk. Tuple-facing output belongs to TupTalk. The Parallel GUI/TUI
lane exists to keep those engine features exposed consistently across
interfaces. It is a direction the surfaces are held to, not a proof: the
Workbench demonstrates it, and the template frontends illustrate it.</p>
