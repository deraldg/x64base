6:T21a3,<h2 id="what-it-does"><a class="no-underline" href="#what-it-does">What it does</a></h2>
<p>SQLsel names the SQL-facing query workflows in DotTalk++ / x64base.</p>
<p>Its subject is set-oriented retrieval rather than cursor navigation. It covers:</p>
<ul>
<li>a <code>SELECT</code> statement over one or more open work areas</li>
<li><code>WHERE</code> filtering, <code>ORDER BY</code> with direction, <code>LIMIT</code>, <code>DISTINCT</code></li>
<li><code>INNER</code>, <code>LEFT</code>, <code>RIGHT</code>, <code>FULL</code> and <code>CROSS</code> joins</li>
<li>aggregates -- <code>COUNT</code>, <code>SUM</code>, <code>AVG</code>, <code>MIN</code>, <code>MAX</code> -- with <code>GROUP BY</code> and <code>HAVING</code></li>
<li>set operations: <code>UNION</code>, <code>UNION ALL</code>, <code>INTERSECT</code>, <code>EXCEPT</code></li>
<li>subqueries: <code>IN (&#x3C;select>)</code> and <code>[NOT] EXISTS (&#x3C;select>)</code></li>
<li>expression projection, so <code>TRIM(LNAME)</code> is a column</li>
<li>DML -- <code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code> -- and explicit transactions under SQL mode</li>
<li>statement scoping: no session state read, no cursor left moved</li>
</ul>
<p><code>SELECT</code> is optional. <code>SQLSEL</code> is itself the verb, and <code>SQLSEL SELECT ...</code> also
parses -- not to be confused with xBase <code>SELECT &#x3C;area></code>, which switches the
active work area.</p>
<p>Real local command surfaces include:</p>
<pre><code class="language-text">SQLSEL SID,LNAME FROM STUDENTS WHERE MAJOR = "CSCI"
SQLSEL SID,LNAME FROM STUDENTS ORDER BY LNAME DESC LIMIT 2
SQLSEL COUNT(*) FROM STUDENTS WHERE GPA >= 3.0
SQLSEL S.LNAME,E.COURSE FROM STUDENTS AS S JOIN ENROLL AS E ON S.SID = E.SID
SQLSEL S.LNAME,E.COURSE FROM STUDENTS AS S LEFT JOIN ENROLL AS E ON S.SID = E.SID
SQLSEL MAJOR,COUNT(*),AVG(GPA) FROM STUDENTS GROUP BY MAJOR HAVING COUNT(*) > 5
SQLSEL DISTINCT MAJOR FROM STUDENTS
SQLSEL SID FROM STUDENTS WHERE SID IN (SQLSEL SID FROM ENROLL)
SQLSEL UPDATE STUDENTS SET GPA = 4.0 WHERE SID = 50000000
SQLSEL USAGE
</code></pre>
<h2 id="statement-scoping"><a class="no-underline" href="#statement-scoping">Statement scoping</a></h2>
<p>A SQLsel statement names its own table and does not consult session state. It
ignores any active <code>SET FILTER</code>, does not depend on the current work area, and
restores every cursor it moves. Two consequences worth knowing:</p>
<ul>
<li>the same statement returns the same rows regardless of where you were
positioned or what filter was set</li>
<li>it reads <strong>committed</strong> table truth, so under <code>TABLE BUFFER ON</code> an uncommitted
edit is not visible to it</li>
</ul>
<p>The second is a deliberate ruling rather than an accident. A statement that
filtered on committed data but displayed buffered data would return a row that
visibly fails its own <code>WHERE</code> clause.</p>
<h2 id="verification"><a class="no-underline" href="#verification">Verification</a></h2>
<p>Every SQLsel regression compares its result sets against an <strong>in-process SQLite
oracle over identical data in the same run</strong> -- not against a recorded expectation,
so a shared misunderstanding between our writer and our reader cannot pass.</p>
<p><strong>Six run in the default suite on every <code>REGRESSION ALL</code>:</strong></p>

































<table><thead><tr><th>spec</th><th>what it holds</th></tr></thead><tbody><tr><td><code>SQLSEL_SELECT_V1</code></td><td>projection, <code>WHERE</code>, <code>ORDER BY</code> before <code>LIMIT</code>, <code>COUNT(*)</code>, expression projection, seven corrective refusals, cursor restoration checked by data</td></tr><tr><td><code>SQLSEL_INNER_JOIN</code></td><td>inner join, alias qualification, both access paths, cursor restoration on both sides</td></tr><tr><td><code>SQLSEL_LEFT_JOIN</code></td><td>left join, <code>&#x3C;UNMATCHED></code> distinct from a genuine blank, outer <code>WHERE</code> and UNKNOWN, the left-extension count reported</td></tr><tr><td><code>SQLSEL_JOIN_FAMILY</code></td><td><code>RIGHT</code>, <code>FULL</code> and <code>CROSS</code>, including the Cartesian count</td></tr><tr><td><code>SQLSEL_JOIN_EDGES</code></td><td>numeric and character keys, seek and scan agreeing row for row, a caller's table lock preserved across the statement</td></tr><tr><td><code>SQLSEL_BUFFER_VIS</code></td><td>committed-versus-buffered visibility, rollback and commit distinguished</td></tr></tbody></table>
<p><strong>Seven more are explicit-run rather than default</strong>, and that distinction is worth
stating rather than blurring: <code>SQLSEL_SET_OPS</code>, <code>SQLSEL_AGGREGATES</code>,
<code>SQLSEL_SUBQUERIES</code>, <code>SQLSEL_ADVANCED_JOIN</code>, <code>SQLSEL_DML</code>, <code>SQLSEL_WORKSPACE</code> and
<code>SQLMODE_SMOKE</code>. Those features ship and have oracle-compared specs; those specs
are not yet in the suite that runs every time.</p>
<h2 id="what-a-join-does-that-a-reader-should-know-in-advance"><a class="no-underline" href="#what-a-join-does-that-a-reader-should-know-in-advance">What a join does that a reader should know in advance</a></h2>
<ul>
<li><strong>Nothing is declared.</strong> No <code>REL</code> or <code>SET RELATION</code> state is read. A join names
its own tables and its own <code>ON</code> columns.</li>
<li><strong>Both tables must already be open.</strong> SQLsel reads open work areas and does not
open files. <code>INNER</code>, <code>LEFT</code> and <code>CROSS</code> may chain across three or more.</li>
<li><strong>Produced absence is not a blank.</strong> An unmatched outer row renders
<code>&#x3C;UNMATCHED></code>; a genuine empty cell in the DBF stays empty. The two are
different facts and the output says which one it is.</li>
<li><strong><code>WHERE</code> runs after outer extension</strong>, so a comparison against a produced-absent
cell is UNKNOWN and <code>WHERE</code> keeps only TRUE -- which is what makes
<code>WHERE &#x3C;right column> IS absent</code> behave the way SQL readers expect.</li>
<li><strong>The access path is reported</strong>, not guessed at: a join prints whether it took a
CDX seek on the inner table with its probe and candidate counts, or a
nested-loop scan with both row counts.</li>
<li><strong>A join takes a non-blocking two-table read fence.</strong> Lock contention refuses
the statement before either table is read, rather than half-reading it.</li>
</ul>
<h2 id="gaps-stated"><a class="no-underline" href="#gaps-stated">Gaps, stated</a></h2>
<p>Corrected 2026-09-09: this list opened with "the bare <code>SELECT ...</code> alias is
still planned", one line above a bullet stating that explicit transactions
<em>require SQL mode</em>. Both cannot be true, and the second one was. <code>SET MODE SQL</code>
routes <code>SELECT</code> (and six other verbs) to <code>SQLSEL</code>, proven against SQLite by the
<code>SQLMODE_SMOKE</code> regression. See
<a href="/docs/engine/sqlsel-and-sql-conformance">SQLsel and SQL Conformance</a>.</p>
<ul>
<li><strong>Explicit transactions require SQL mode and accept ONE target table.</strong>
Cross-table atomic commit is refused.</li>
<li><strong>No stored NULL in DML, and no memo-field DML.</strong> Both are refused rather than
silently coerced.</li>
<li><strong>A subquery over a joined outer scope is refused.</strong> Correlated subqueries over
a single outer table work and report their actual evaluation count.</li>
<li><strong>It reads committed table truth.</strong> Under <code>TABLE BUFFER ON</code> an uncommitted edit
is not visible to a statement -- see Statement scoping above, where that is
argued as a ruling rather than a limitation.</li>
</ul>
