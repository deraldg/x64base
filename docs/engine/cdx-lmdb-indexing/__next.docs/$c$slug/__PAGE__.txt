<h2 id="teaching-model"><a class="no-underline" href="#teaching-model">Teaching Model</a></h2>
<p>The learner-visible model is a chain, and the order of its links is the lesson:</p>
<p><strong>index -> index flavor -> order</strong></p>
<ol>
<li>A table stores records.</li>
<li><code>SET INDEX</code> attaches a container. <strong>This is where the flavor is decided</strong> -- <code>.cnx</code>, <code>.cdx</code> or <code>.inx</code> -- not later.</li>
<li><code>SET ORDER</code> selects a named tag <em>inside</em> the flavor already chosen.</li>
<li>An active order changes navigation without changing physical record order.</li>
</ol>
<p>With no container attached you get logical, natural record order. That is the
absence of an index rather than a fourth flavor.</p>
<h2 id="cdxs-backend-depends-on-where-the-table-lives"><a class="no-underline" href="#cdxs-backend-depends-on-where-the-table-lives">CDX's backend depends on where the table lives</a></h2>
<p>This is the part most easily got wrong, because "CDX means LMDB" is true only
on disk:</p>




















<table><thead><tr><th>residence</th><th>CDX backend</th><th>maintains on mutation?</th></tr></thead><tbody><tr><td>disk</td><td>LMDB environment</td><td>yes</td></tr><tr><td>vRAM</td><td>native CDX-V64</td><td><strong>no</strong> -- marks the container stale</td></tr></tbody></table>
<p><strong>LMDB cannot live in vRAM.</strong> <code>include/xbase/ramfs.hpp</code> states the reason
plainly: LMDB "must mmap a real OS file", and the RAM filesystem has none. So
<code>index_manager.cpp</code> routes RAM-resident tables to a "native CDX-V64 backend
(uint64, LMDB-free) served from RAM", skipping the LMDB environment gate
entirely. That native backend does not incrementally maintain: its <code>upsert</code> and
<code>erase</code> mark the container stale and a rebuild reconstructs it.</p>
<h2 id="why-cnx-was-reactivated-for-v64"><a class="no-underline" href="#why-cnx-was-reactivated-for-v64">Why CNX was reactivated for v64</a></h2>
<p>That constraint is the reason, and it is worth stating as cause and effect
rather than as two unrelated facts.</p>
<p>CNX gained realtime index maintenance specifically to serve RAM-resident
tables -- <code>cnx_backend.cpp</code> says the RAM/vdisk case is "the case this milestone
exists to serve". Since LMDB-backed CDX is unavailable in vRAM and native CDX
goes stale on mutation, CNX is the flavor that stays correct there.</p>
<p>So an owner ruling on 2026-08-09 reactivated CNX for v64 tables: an explicit
<code>.cnx</code> is accepted on a v64 table with an advisory, where it was previously a
hard refusal. Two things did <strong>not</strong> change, and both matter:</p>
<ul>
<li><strong>The default is untouched.</strong> With no extension given, v64 still resolves to
<code>.cdx</code>. CNX only auto-resolves when a <code>.cnx</code> exists and no <code>.cdx</code> does, and
it says so: "no .cdx container found; using existing CNX (LMDB-backed CDX is
the preferred x64 index)."</li>
<li><strong>Nothing substitutes automatically.</strong> The engine does not swap CDX for CNX
because a table is in RAM. The choice is explicit and travels per table in
the workspace posture (<code>index=</code> / <code>indextype=</code>), which is what lets one
workspace mix CNX, CDX and INX.</li>
</ul>
<p>CDX is the container, creator, and manager surface for indexes in the xBase
lineage. LMDB is the embedded database technology used underneath the modern
x64base implementation <strong>on disk</strong>.</p>
<h2 id="source-evidence"><a class="no-underline" href="#source-evidence">Source Evidence</a></h2>
<p>The current source tree shows this split in several places:</p>
<ul>
<li><code>include/cdx/cdx.hpp</code> defines the minimal CDX container contract: header I/O, table binding, tag directory read/write, and add/drop tag operations.</li>
<li><code>src/cli/cmd_cdx.cpp</code> exposes CDX container management commands.</li>
<li><code>src/cli/cmd_buildlmdb.cpp</code> builds or rebuilds the LMDB backing store for a CDX container.</li>
<li><code>src/cli/cmd_setorder.cpp</code> documents the policy: <strong>disk-resident</strong> v64 tables use a CDX container backed by LMDB; public CDX paths resolve under <code>INDEXES</code>, while backend LMDB paths resolve under <code>LMDB</code>. The same file carries the 2026-08-09 CNX-on-v64 ruling and its advisory.</li>
<li><code>src/cli/cmd_setindex.cpp</code> calls itself a "Flavor-aware decision flow" and is where the flavor is chosen: classic xBase/VFP accepts <code>.inx</code> / <code>.cnx</code>, true x64/v128 prefers <code>.cdx</code>. Attach and tag activation are "two related decisions" -- which is the <code>index -> index flavor -> order</code> chain above.</li>
<li><code>include/xbase/ramfs.hpp</code> records why the vRAM lane differs: LMDB "must mmap a real OS file", so it is out of scope for the RAM filesystem.</li>
<li><code>src/xindex/index_manager.cpp</code> routes RAM-resident tables to the "native CDX-V64 backend (uint64, LMDB-free) served from RAM", skipping the LMDB environment gate.</li>
<li><code>src/xindex/cdx_native_backend.cpp</code> states the native backend's limit in its own comment: it "does not incrementally maintain on mutation in v1", so <code>upsert</code> and <code>erase</code> mark the container stale.</li>
<li><code>src/xindex/cnx_backend.cpp</code> records why CNX gained realtime maintenance: "RAM/vdisk tables are the case this milestone exists to serve."</li>
<li><code>docs/cases/CASE_ENG_010_INDEX_NAVIGATION_CDX_LMDB.md</code> states the teaching rule directly: CDX is the user-facing logical container, and LMDB is a backend implementation detail.</li>
</ul>
<h2 id="operational-flow"><a class="no-underline" href="#operational-flow">Operational Flow</a></h2>
<pre><code class="language-text">DBF_64 / table area
  -> CDX container
       -> tag directory
       -> table binding
       -> logical order names
  -> BUILDLMDB
       -> LMDB environment
       -> named backend databases for tags
  -> SET ORDER / SEEK / INDEXSEEK / LIST_LMDB
       -> ordered navigation and diagnostics
</code></pre>
<p>In the lab campus, this gives us a clean horizontal slice. A student can see record storage, index metadata, backend materialization, and navigation behavior as separate layers of the same system.</p>

<h2 id="why-this-fits-labtalk"><a class="no-underline" href="#why-this-fits-labtalk">Why This Fits LabTalk</a></h2>
<p>LabTalk is a laboratory campus, so the index system should be presented as a set of rooms:</p>
<ul>
<li><strong>Records room</strong> - physical table rows and record numbers.</li>
<li><strong>Container room</strong> - CDX headers, table binding, and tag directory.</li>
<li><strong>Backend room</strong> - LMDB environment, named databases, and rebuild lifecycle.</li>
<li><strong>Navigation room</strong> - <code>SET ORDER</code>, <code>SEEK</code>, <code>SKIP</code>, <code>TOP</code>, and <code>BOTTOM</code>.</li>
<li><strong>Diagnostics room</strong> - command output, case stories, runtime proofs, and SelfDoc contracts.</li>
</ul>
<p>This lets the same feature serve CS101, database history, systems programming, and advanced runtime inspection without changing the underlying architecture.</p>
