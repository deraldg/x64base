19:T2231,<p>Some of the engine's most distinctive behavior is easy to miss because it was
proven quietly, in regressions and session transcripts, rather than announced.
This page promotes those behaviors to named features -- under one rule: <strong>every
entry states its evidence tier, and nothing here outranks its proof.</strong> Tiers
follow the house convention: <em>runtime-proven</em> (a transcript or regression shows
it), <em>source-evidenced</em> (the mechanism is confirmed in source; the end-to-end
run has not happened), <em>chartered</em> (a designed and registered lane, not yet
built).</p>
<h2 id="one-engine-three-dbf-flavors"><a class="no-underline" href="#one-engine-three-dbf-flavors">One engine, three DBF flavors</a></h2>
<p><strong>Runtime-proven.</strong> The same runtime opens and works classic x32 DBF, the
x64-family format, and Visual FoxPro tables. The teaching datasets ship in all
three (plus a reference copy), and the <code>INDEX_X32</code> and <code>INDEX_X64</code> regressions
exercise flavor-correct behavior on every run. Flavor is a property of the
table, not the build: one executable, three dialects.</p>
<p>Evidence: <code>REGRESSION RUN INDEX_X32</code> / <code>INDEX_X64</code>; the MCC teaching datasets
(x64, x32, VFP, reference); the <a href="/docs/engine/dbf-flavors-and-indexes">DBF flavors and indexes</a>
reference.</p>
<h2 id="an-index-family-not-an-index"><a class="no-underline" href="#an-index-family-not-an-index">An index family, not an index</a></h2>
<p><strong>Runtime-proven, one direction of cross-attachment chartered.</strong> The engine
carries INX and CNX (classic-generation), CDX with an LMDB-backed key store
(x64-generation), and publishes the attach / rebuild / order / seek seams as
architecture rather than sealed internals. Cross-generation attachment is
policy, not accident: a CNX can be explicitly attached to an x64 table with an
advisory (proven by the <code>INDEX_X64_CNX</code> regression, including <code>REINDEX</code>
routing and the unchanged CDX default); the mirror direction (CDX on classic
tables) is a chartered lane awaiting its proof.</p>
<p>Evidence: <code>REGRESSION RUN INDEX_X64_CNX</code>; <a href="/docs/engine/cdx-lmdb-indexing">CDX / LMDB indexing</a>;
the Open Index API section of the <a href="/docs/engine/api-reference">API reference</a>.</p>
<h2 id="whole-tables----and-their-indexes----in-ram"><a class="no-underline" href="#whole-tables----and-their-indexes----in-ram">Whole tables -- and their indexes -- in RAM</a></h2>
<p><strong>Runtime-proven.</strong> The in-process RAM virtual disk (<code>VDISK</code>) hosts complete
x64 tables <em>and their native CDX indexes</em> with zero files on disk: built,
indexed, and traversed in ordered form entirely in memory, then unmounted. The
<code>MEM</code> regression is the standing proof (create, index, ordered read-back,
teardown -- all in RAM).</p>
<p>Evidence: <code>REGRESSION RUN MEM</code>; <code>VDISK STATUS</code> residency checkpoints in its
transcript.</p>
<h2 id="two-relational-consumers-over-one-declared-graph"><a class="no-underline" href="#two-relational-consumers-over-one-declared-graph">Two relational consumers over one declared graph</a></h2>
<p><strong>Runtime-proven, on a production-shaped schema.</strong> The same declared relation
graph is walked by two independent engines: traditional <code>SET RELATION</code>
navigation (position drives the child cursor) and <code>SQLsel</code>, the house
set-oriented SELECT (the qualifying rows come back as a set). On 2026-08-10
both walkers answered the same question over a 34-table ERP schema with 58
foreign-key relations -- and agreed on the answer, down to the record. SQLsel's
row sets are additionally verified against an in-process SQLite oracle in its
own regression, so the second walker's correctness is anchored to an external
implementation.</p>
<p>Evidence: <code>REGRESSION RUN CASCADE_ENV</code> (both walkers in one run);
<code>SQLSEL_SELECT_V1</code> (the oracle harness); the <a href="/schemas">Schemas</a> page for the
graph itself.</p>
<h2 id="a-workspace-that-restores-a-whole-database-posture-from-one-file"><a class="no-underline" href="#a-workspace-that-restores-a-whole-database-posture-from-one-file">A workspace that restores a whole database posture from one file</a></h2>
<p><strong>Runtime-proven.</strong> <code>WORKSPACE SAVE</code> captures open areas, attached indexes,
selected tag orders, aliases, and declared relations into a plain-text
<code>.dtschema</code> snapshot; <code>WORKSPACE LOAD</code> restores all of it. The standing
demonstration restores 43 work areas and 58 relations -- an entire ERP, posed
and ready to relate -- from a single command against one committed file.</p>
<p>Evidence: <code>workspaces/cascade_all.dtschema</code> in the repository;
<code>REGRESSION RUN CASCADE_ENV</code> Section 2.</p>
<h2 id="gui-orthogonal-by-construction"><a class="no-underline" href="#gui-orthogonal-by-construction">GUI-orthogonal by construction</a></h2>
<p><strong>Source-evidenced, enforced as doctrine.</strong> Terminal, TUI, and future GUI
surfaces are consumers of the same runtime truth: ordering, cursor state,
relations, validation, and command execution live in the engine and DotTalk++,
never duplicated in UI logic. A front end can be added or removed without the
database behaving differently -- which is what makes the parallel GUI/TUI lane
a lane rather than a rewrite.</p>
<p>Evidence: the <a href="/docs/dev/application-ui-dsl-lane">Application UI DSL lane</a>;
the workbench front-ends principle on the <a href="/docs/engine/architecture">architecture</a> page.</p>
<h2 id="modular-by-structure-not-by-slogan"><a class="no-underline" href="#modular-by-structure-not-by-slogan">Modular by structure, not by slogan</a></h2>
<p><strong>Source-evidenced -- verifiable from the build itself.</strong> The claim is
checkable in one build log: the engine links as separate libraries with
separate responsibilities -- <code>xbase</code> (tables and work areas), <code>xindex</code>
(indexes), <code>memo</code> (memo storage), <code>xexpr</code> (the expression evaluator),
<code>dottalk_value</code> (the value system), <code>dottalk_tvui</code> (the TUI) -- under the
<code>dottalkpp</code> command host. The execution chain is equally legible: <code>main</code> to
shell, shell to command registry, registry to one <code>cmd_*</code> translation unit per
command, commands to the libraries. Every seam in that sentence is a real
compilation boundary.</p>
<p>Evidence: the CMake target list in any build transcript; the
<a href="/docs/engine/architecture">architecture</a> layering; per-command source contracts
in the command files.</p>
<h2 id="payload-agnostic-memos-and-where-that-is-heading"><a class="no-underline" href="#payload-agnostic-memos-and-where-that-is-heading">Payload-agnostic memos (and where that is heading)</a></h2>
<p><strong>Source-evidenced today; the interesting destination is chartered.</strong> x64
memos are addressed by 64-bit object identifiers and are payload-agnostic by
design -- the memo layer does not care what it stores. That is the confirmed
mechanism. The chartered destination built on it -- memo-resident
mini-databases, where a memo field carries an entire small database as a
teaching payload -- is a registered design lane, stated here at exactly that
tier: designed and intended, not yet runtime-proven.</p>
<p>Evidence: <code>src/memo/memo_ref.cpp</code> (64-bit payload-agnostic MemoRef); the
virtual-workspaces intake package (2026-07-28) for the chartered lane; the
<a href="/docs/engine/fpt64-memo-format">FPT64 memo format</a> reference.</p>
<h2 id="sqlite-in-the-same-room-on-purpose"><a class="no-underline" href="#sqlite-in-the-same-room-on-purpose">SQLite in the same room, on purpose</a></h2>
<p><strong>Runtime-proven.</strong> SQLite is compiled in as a companion carrier and as a
verification instrument: dual-carrier teaching systems keep a sealed SQLite
authority beside their x64base mirrors, the <code>ERP</code> and <code>SQLITE</code> command
families open and query it natively, and the house SELECT checks its answers
against a SQLite oracle. Competing with SQLite and using it as the referee are
the same decision, made deliberately.</p>
<p>Evidence: <code>ERP CHECK</code> scorecards in the Cascade transcripts; the
<a href="/schemas">Schemas</a> dual-carrier contract; <code>SQLSEL_SELECT_V1</code>.</p>
