6:T4687,<p>Some of the engine's most distinctive behavior is easy to miss because it was
proven quietly, in regressions and session transcripts, rather than announced.
This page promotes those behaviors to named features -- under one rule: <strong>every
entry states its evidence tier, and nothing here outranks its proof.</strong> Tiers
follow the house convention: <em>runtime-proven</em> (a transcript or regression shows
it), <em>source-evidenced</em> (the mechanism is confirmed in source; the end-to-end
run has not happened), <em>chartered</em> (a designed and registered lane, not yet
built).</p>
<h2 id="one-engine-three-dbf-flavors"><a class="no-underline" href="#one-engine-three-dbf-flavors">One engine, three DBF flavors</a></h2>
<p><strong>Runtime-proven.</strong> The same runtime opens and works classic x32 DBF, the
x64-family format, and Visual FoxPro tables. The teaching datasets ship in all
three (plus a reference copy), and the <code>INDEX_X32</code> and <code>INDEX_X64</code> regressions
exercise flavor-correct behavior on every run. Flavor is a property of the
table, not the build: one executable, three dialects.</p>
<p>Evidence: <code>REGRESSION RUN INDEX_X32</code> / <code>INDEX_X64</code>; the MCC teaching datasets
(x64, x32, VFP, reference); the <a href="/docs/engine/dbf-flavors-and-indexes">DBF flavors and indexes</a>
reference.</p>
<h2 id="an-index-family-not-an-index"><a class="no-underline" href="#an-index-family-not-an-index">An index family, not an index</a></h2>
<p><strong>Runtime-proven, one direction of cross-attachment chartered.</strong> The engine
carries INX and CNX (classic-generation), CDX with an LMDB-backed key store
(x64-generation), and publishes the attach / rebuild / order / seek seams as
architecture rather than sealed internals. Cross-generation attachment is
policy, not accident: a CNX can be explicitly attached to an x64 table with an
advisory (proven by the <code>INDEX_X64_CNX</code> regression, including <code>REINDEX</code>
routing and the unchanged CDX default); the mirror direction (CDX on classic
tables) is a chartered lane awaiting its proof.</p>
<p>Evidence: <code>REGRESSION RUN INDEX_X64_CNX</code>; <a href="/docs/engine/cdx-lmdb-indexing">CDX / LMDB indexing</a>;
the Open Index API section of the <a href="/docs/engine/api-reference">API reference</a>.</p>
<h2 id="whole-tables----and-their-indexes----in-ram"><a class="no-underline" href="#whole-tables----and-their-indexes----in-ram">Whole tables -- and their indexes -- in RAM</a></h2>
<p><strong>Runtime-proven.</strong> The in-process RAM virtual disk (<code>VDISK</code>) hosts complete
x64 tables <em>and their native CDX indexes</em> with zero files on disk: built,
indexed, and traversed in ordered form entirely in memory, then unmounted. The
<code>MEM</code> regression is the standing proof (create, index, ordered read-back,
teardown -- all in RAM).</p>
<p>That same virtual disk is now a hydration target: a saved workspace can be
stood up <em>into</em> RAM on demand -- 24 files and 92 KB of tables and indexes in
under a tenth of a second -- and dropped again by unmounting, with the disk
originals untouched. The residency claim is cross-checked rather than
asserted: the copier's byte count and the RAM disk's own census are compared
every run, and they agree exactly.</p>
<p>Evidence: <code>REGRESSION RUN MEM</code>; <code>WORKSPACE_RAM</code> (timed hydration + census
cross-check); <code>VDISK STATUS</code> residency checkpoints in both transcripts.</p>
<h2 id="two-relational-consumers-over-one-declared-graph"><a class="no-underline" href="#two-relational-consumers-over-one-declared-graph">Two relational consumers over one declared graph</a></h2>
<p><strong>Runtime-proven, on a production-shaped schema.</strong> The same declared relation
graph is walked by two independent engines: traditional <code>SET RELATION</code>
navigation (position drives the child cursor) and <code>SQLsel</code>, the house
set-oriented SELECT (the qualifying rows come back as a set). On 2026-08-10
both walkers answered the same question over a 34-table ERP schema with 58
foreign-key relations -- and agreed on the answer, down to the record. SQLsel's
row sets are additionally verified against an in-process SQLite oracle in its
own regression, so the second walker's correctness is anchored to an external
implementation.</p>
<p>Evidence: <code>REGRESSION RUN CASCADE_ENV</code> (both walkers in one run);
<code>SQLSEL_SELECT_V1</code> (the oracle harness); the <a href="/schemas">Schemas</a> page for the
graph itself.</p>
<h2 id="a-workspace-that-restores-a-whole-working-session"><a class="no-underline" href="#a-workspace-that-restores-a-whole-working-session">A workspace that restores a whole working session</a></h2>
<p><strong>Runtime-proven.</strong> <code>WORKSPACE SAVE</code> captures open areas, attached indexes,
selected tag orders, aliases, and declared relations into a plain-text
<code>.dtschema</code> snapshot; <code>WORKSPACE LOAD</code> restores all of it. The standing
demonstration restores 43 work areas and 58 relations -- an entire ERP, posed
and ready to relate -- from a single command.</p>
<p>Two later increments turned a schema snapshot into a session snapshot:</p>
<ul>
<li><strong>Self-locating postures.</strong> A version-3 snapshot records the roots its
tables live under, and a restore resolves against <em>those</em> rather than
whatever environment happens to be set. The proof deliberately breaks the
environment first -- points the engine at the wrong directories -- and the
workspace still stands up, because the posture knows where it lives.
Version 2 is untouched and still the default; the new lines are additive,
and older readers skip them.</li>
<li><strong>Session state, not just structure.</strong> A version-3 save also records where
each area's cursor sat and which area was selected. A restore puts them
back and then refreshes relations, so child tables re-slave to the
<em>restored</em> parent positions. The standing proof drives a sales-order parent
to its last record, saves, tears the whole workspace down, reloads, and
finds parent and slaved child exactly where they were -- 43 cursors
restored, verified by the engine's own position reporter.</li>
</ul>
<p>Evidence: <code>workspaces/cascade_all.dtschema</code>; <code>REGRESSION RUN CASCADE_ENV</code>
Section 2; <code>WORKSPACE_V3</code> (self-location from a broken environment);
<code>WORKSPACE_SESSION</code> (cursors, selection, refresh).</p>
<h2 id="gui-orthogonal-by-construction"><a class="no-underline" href="#gui-orthogonal-by-construction">GUI-orthogonal by construction</a></h2>
<p><strong>Source-evidenced, enforced as doctrine.</strong> Terminal, TUI, and future GUI
surfaces are consumers of the same runtime truth: ordering, cursor state,
relations, validation, and command execution live in the engine and DotTalk++,
never duplicated in UI logic. A front end can be added or removed without the
database behaving differently -- which is what makes the parallel GUI/TUI lane
a lane rather than a rewrite.</p>
<p>Evidence: the <a href="/docs/dev/application-ui-dsl-lane">Application UI DSL lane</a>;
the workbench front-ends principle on the <a href="/docs/engine/architecture">architecture</a> page.</p>
<h2 id="modular-by-structure-not-by-slogan"><a class="no-underline" href="#modular-by-structure-not-by-slogan">Modular by structure, not by slogan</a></h2>
<p><strong>Source-evidenced -- verifiable from the build itself.</strong> The claim is
checkable in one build log: the engine links as separate libraries with
separate responsibilities -- <code>xbase</code> (tables and work areas), <code>xindex</code>
(indexes), <code>memo</code> (memo storage), <code>xexpr</code> (the expression evaluator),
<code>dottalk_value</code> (the value system), <code>dottalk_tvui</code> (the TUI) -- under the
<code>dottalkpp</code> command host. The execution chain is equally legible: <code>main</code> to
shell, shell to command registry, registry to one <code>cmd_*</code> translation unit per
command, commands to the libraries. Every seam in that sentence is a real
compilation boundary.</p>
<p>Evidence: the CMake target list in any build transcript; the
<a href="/docs/engine/architecture">architecture</a> layering; per-command source contracts
in the command files.</p>
<h2 id="payload-agnostic-memos-proven-by-adversary"><a class="no-underline" href="#payload-agnostic-memos-proven-by-adversary">Payload-agnostic memos, proven by adversary</a></h2>
<p><strong>Runtime-proven.</strong> x64 memos are addressed by 64-bit object identifiers and
do not inspect what they store -- and that claim is no longer taken on the
source's word. A seeded stress harness drives six chaotic operation patterns
against the store (self-mutation, cross-memo prefix overwrites, growth and
shedding, duplication, merge-and-erase, emptying and erasure), with payloads
that deliberately include embedded NUL and high bytes, while an in-memory
shadow model byte-compares every stored object after every generation. Four
seeds: 20,500 generations, 104,044 operations, roughly 215 close/reopen
cycles, <strong>zero divergences</strong>. Byte fidelity, cross-memo isolation, reopen
durability, and payload agnosticism all held. Every run replays exactly from
its seed.</p>
<p>The harness came from an unusual place: an external AI (Microsoft Copilot)
supplied a whimsical "memo zoo" stress spec, which was mapped rather than
adopted -- its creature species became <em>driver personas</em>, because our memos
have no behavior and that absence is precisely the claim under test. The zoo
proves the cage.</p>
<p>Evidence: <code>src/memo/memo_zoo.cpp</code> (seeded harness, shadow-model oracle);
<code>src/memo/memo_smoke.cpp</code>; <code>src/memo/memo_ref.cpp</code> (64-bit payload-agnostic
MemoRef); the <a href="/docs/engine/fpt64-memo-format">FPT64 memo format</a> reference.
Not claimed: contention. Concurrency at the memo layer is a named, unrun
milestone -- a second process holding the cooperative table lock while the
zoo runs.</p>
<h2 id="memo-fields-that-survive-the-round-trip"><a class="no-underline" href="#memo-fields-that-survive-the-round-trip">Memo fields that survive the round trip</a></h2>
<p><strong>Runtime-proven, with a correction recorded.</strong> A memo field on an x64 table
can be written, closed, reopened, and read back as <em>text</em> -- and updated
again after the reopen. That sounds unremarkable until you know the history:
a canary written in May 2026 recorded exactly those two behaviors as broken
(a reopened memo read back as its internal reference token, and a subsequent
update reported the backend detached). A routine request in August -- add a
memo field to a students-shaped table, put a string in it -- re-measured both
cases green and retired a three-month-old defect by accident. The canary was
not wrong; its subject moved, and the record says so.</p>
<p>The same day's tooling then caught this entry's first draft overclaiming.
The demonstration built its table in the RAM virtual disk and reported
writing nothing to disk; a residency check measured the memo's sidecar file
landing on real disk, because the memo store does its own file I/O and
bypasses the virtual filesystem. The table was in RAM; the memo was not. The
claim was corrected in place, and RAM coverage for the memo store is now a
named prerequisite rather than an assumption.</p>
<p>Evidence: <code>REGRESSION RUN MEMO_RAM_HELLO</code> (write, reopen readback, update
after reopen); the 2026-05-13 canary retained in the script tree with its
status updated rather than deleted.</p>
<h2 id="a-database-posture-that-lives-inside-the-database"><a class="no-underline" href="#a-database-posture-that-lives-inside-the-database">A database posture that lives inside the database</a></h2>
<p><strong>Runtime-proven; the larger destination stays chartered.</strong> <code>WORKSPACE SAVE &#x3C;name> MEMO</code> serializes the entire open posture -- work areas, attached
indexes, selected tag orders, aliases, and every declared relation -- into a
memo field of a self-creating catalog table, and <code>WORKSPACE LOAD &#x3C;name> MEMO</code>
restores it from inside that table. The snapshot text is byte-identical in
either carrier (one format, two carriers), so there is no second serializer
to drift. Each catalog row records the author (real member attribution), the
timestamp, and the path roots active at save time -- snapshots are
root-relative, so each one declares its own preconditions -- and history is
append-only, with a re-save superseding rather than overwriting. Every save
is verified: the payload is read back through the token <em>stored in the field</em>
and byte-compared, loudly failing on mismatch.</p>
<p>The standing demonstration restores 43 work areas and 58 relations from a
memo and then walks the restored graph both ways -- positional traversal and
the house SELECT -- which agree to the record. Workspaces became data:
queryable, relatable, attributed, versioned, and verifiable in the same store
they describe.</p>
<p>The same afternoon the catalog grew into a <em>table of workspaces</em>: a v2 schema
with a unique auto-id, carrier-flavored instance identity stamped into every
serialized posture, dimensions measured from the open areas rather than
declared, recursion-guard columns, and supersede lineage that doubles as a
version chain. Format version 3 landed opt-in beside the proven version 2:
a v3 posture is <em>self-locating</em> -- it records its own dbf/index roots and a
restore resolves against them, proven by restoring 13 areas from a
deliberately mis-set environment. A posture can also hydrate straight into
the in-process RAM filesystem, timed rather than adjectived: 24 files and
92 KB stood up in the 71-94 ms range, with the RAM census agreeing with the
hydration counter byte for byte, and dismissal (unmount) dropping every RAM
file while disk stays untouched. And a v3 save now captures <em>session state</em>:
per-area cursor positions and the selected area ride in the payload, so a
restore resumes exactly where work stopped -- the standing proof drives a
sales-order parent to its last record, saves, tears everything down,
reloads, and finds parent and slaved child exactly where they were.</p>
<p>By evening the chartered destination itself landed, first try: a
<strong>memo-resident mini-database</strong>. One save carries the posture <em>and</em> every
table's bytes and every attached index's bytes in a binary-safe container --
the whole 13-table teaching database, 94 KB, inside one memo field,
byte-compare verified as a unit. Loading it back needs no disk at all: onto
a clean RAM disk, 24 files hydrated <em>from the memo</em> in 65 ms with zero disk
reads, rows readable and indexes attaching from memo-carried bytes. A whole
small database now lives inside a field of another database -- versioned by
the catalog's supersede chain, attributed, and verifiable, the design the
2026-07-28 external intake chartered.</p>
<p>What remains chartered: the commit/rollback writeback cycle from RAM to
disk, and memo carriage for LMDB (out of the RAM filesystem's scope by its
own contract). One correction from the same day is recorded rather than
smoothed: an earlier RAM-memo demonstration claimed zero disk writes, and
the day's own hydration tooling measured the memo sidecar landing on real
disk -- the claim was corrected in place and RAM coverage for the memo
store is now the chartered prerequisite.</p>
<p>Evidence: <code>REGRESSION RUN WORKSPACE_MEMO</code> / <code>WORKSPACE_V3</code> / <code>WORKSPACE_RAM</code>
/ <code>WORKSPACE_SESSION</code> / <code>WORKSPACE_MINIDB</code>; the <code>WORKSPACES</code> catalog in the
runtime data root; the virtual-workspaces design package (2026-07-28), now
partially realized at runtime.</p>
<h2 id="sqlite-in-the-same-room-on-purpose"><a class="no-underline" href="#sqlite-in-the-same-room-on-purpose">SQLite in the same room, on purpose</a></h2>
<p><strong>Runtime-proven.</strong> SQLite is compiled in as a companion carrier and as a
verification instrument: dual-carrier teaching systems keep a sealed SQLite
authority beside their x64base mirrors, the <code>ERP</code> and <code>SQLITE</code> command
families open and query it natively, and the house SELECT checks its answers
against a SQLite oracle. Competing with SQLite and using it as the referee are
the same decision, made deliberately.</p>
<p>Evidence: <code>ERP CHECK</code> scorecards in the Cascade transcripts; the
<a href="/schemas">Schemas</a> dual-carrier contract; <code>SQLSEL_SELECT_V1</code>.</p>
<h2 id="self-measuring-governance"><a class="no-underline" href="#self-measuring-governance">Self-measuring governance</a></h2>
<p><strong>Runtime-proven -- on the project itself.</strong> The same measurement discipline
the engine applies to data is applied to the project's own governance. The
maintainers' rulings page is generated per request from canonical sources
("nothing on this page is hand-entered"), and on 2026-08-10 its
derived-versus-declared reconciliation caught its own maintainers: a hand-kept

same evening and the derived figure owns the count now -- with the incident
kept visible as the page's own history rather than erased. A check that has
never disagreed with its operators has never been tested; this one disagreed
and was right.</p>
<p>Evidence: the retirement sentinel and parser recognition in the source tree
