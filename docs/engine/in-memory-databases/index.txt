DBF-family engine — tables, native CDX-V64 indexes, relations, scripts — entirely
in RAM, with <strong>no change to the record, create, or loader code</strong>. Residency comes

<h2 id="two-substrates"><a class="no-underline" href="#two-substrates">Two substrates</a></h2>
<p>The initiative deliberately has two RAM substrates, chosen so the engine owns as
much of the mechanism as possible.</p>
<p>The <strong>primary substrate is a self-owned in-process virtual filesystem</strong>
(<code>xbase::ramfs</code>). It is the modern re-implementation of the 1980s <code>RAMDRIVE.SYS</code>
/ <code>VDISK.SYS</code> idea, but owned by the engine instead of the operating system — no
signed kernel driver, no drive letter, and no third-party license to vet for
redistribution. A process-global registry maps normalized absolute paths to
growable byte buffers (<code>RamFile</code>s). The DBF and native-CDX file layers simply
consult that registry: a virtual path reads and writes a RAM buffer, a real path
uses the OS. Because the entire file stack runs unchanged, a table created in RAM
behaves exactly like its on-disk twin — <code>USE</code> can reopen it and its sibling
<code>.cdx</code> still resolves, since RAM files persist in the registry across stream
open and close.</p>
<p>The <strong>optional add-on is LMDB-in-RAM via an operating-system symlink.</strong> LMDB must
<code>mmap</code> a real OS file, so it cannot live in the in-process VFS. If a user wants
LMDB-backed index environments in RAM as well, they opt into a symlink or
junction that points the <code>mem</code> path slots at a real RAM volume — <code>/dev/shm</code>
(tmpfs) on Linux with zero setup, or a driver-backed RAM disk on Windows. This is
the only path that needs the <code>vdisk.ini</code> administrator configuration.</p>
<h2 id="the-vdisk-lane"><a class="no-underline" href="#the-vdisk-lane">The VDISK lane</a></h2>
<p><code>VDISK MOUNT</code> redirects the DBF, INDEXES, and LMDB path slots beneath the RAM
root (default <code>&#x3C;DATA>/ram</code>) and mounts it as an in-process <code>ramfs</code> root. While
mounted, <code>CREATE X64</code>, <code>USE</code>, and native CDX-V64 all live in RAM with nothing
written to disk; <code>VDISK STATUS</code> and <code>VDISK CONFIG</code> report the live state; and
<code>VDISK UNMOUNT</code> / <code>OFF</code> / <code>CLEAR</code> drop every resident RAM file. The lane is
deliberately <strong>ephemeral</strong> — data that must survive belongs in a durable table or
an explicit export. The full command and lifetime contract, owned by
<code>src/cli/cmd_vdisk.cpp</code>, is documented on
<a href="/docs/engine/ram-dbf-vdisk">RAM DBF and VDISK</a>.</p>
<h2 id="two-layer-sizing-and-governance"><a class="no-underline" href="#two-layer-sizing-and-governance">Two-layer sizing and governance</a></h2>
<p>The <em>hard</em> size limit belongs to the OS mount (tmpfs or a RAM-disk driver), which
the engine did not create and cannot unilaterally resize. So sizing is split into
two honest layers, per the AIF-043 spec (<em>VDISK RAM Sizing &#x26; Admin Config v1</em>).</p>
<p><strong>Layer 1 is a provisioning recommendation — advisory, not enforced.</strong> In
<code>mode = auto</code> the engine computes a suggested volume size as
<code>clamp(25% × available RAM, 64 MB floor, 2 GB ceiling)</code>, then caps it at 50% of
total RAM so it never starves the host. A 16 GB machine with 10 GB free is advised
2 GB; a 4 GB machine with 1.5 GB free, 384 MB; a 1 GB machine with 300 MB free,
75 MB — degrading gracefully. <code>VDISK CONFIG</code> reports this number for an
administrator or a provisioning script to act on.</p>
<p><strong>Layer 2 is the engine's own soft budget — owned and enforced.</strong> The engine
tracks <code>used_bytes</code> for files under the RAM root, warns at a high-water mark
(<code>warn_pct</code>, default 80%), and applies an <code>on_full</code> policy at 100%: <code>warn</code> (let
the OS write fail with a clear message), <code>spill</code> (fall back to the real-disk slot,
converting RAM to disk), or <code>fail</code>. <code>VDISK STATUS</code> reports the live counter and
resident-file count. This layer stays portable and honest even when the OS mount
size is out of the engine's hands.</p>
<p>The <code>vdisk.ini</code> file ships <strong>inert</strong> — every line commented, so the feature is off
until a user opts in. It is a true INI file (not a DotScript), read by its own
<code>[vdisk]</code> parser with keys for <code>enabled</code>, <code>root</code>, <code>mode</code>, <code>size_mb</code>, <code>percent</code>,
<code>floor_mb</code>, <code>ceil_mb</code>, <code>warn_pct</code>, and <code>on_full</code>.</p>
<h2 id="proposed-direction--virtual-workspaces-and-memo-resident-mini-databases"><a class="no-underline" href="#proposed-direction--virtual-workspaces-and-memo-resident-mini-databases">Proposed direction — virtual workspaces and memo-resident mini-databases</a></h2>
<blockquote>
<p><strong>Status: external design intake, not implemented.</strong> Recorded on the
development side as intake package <code>AIPR-20260728-GROK-002</code> (proposed
<code>AIF-070</code>), an architecture proposal from xAI Grok reviewed by the local
workbench on 2026-07-28. It mutates no source and carries no runtime proof. It
is described here as a forward direction, not a current capability.</p>
</blockquote>
<p>The next design question builds on two existing primitives: the DTSHEMA workspace
format (<code>src/workspace/schema_workspace.cpp</code>) and the payload-agnostic 64-bit
memo reference (<code>MemoRef</code>, <code>src/memo/memo_ref.cpp</code>). The proposal explores
<strong>concurrent named workspaces</strong> with first-class area ownership and <strong>area
budgeting</strong>, replacing today's manual area-partitioning technique with a
supported one; and <strong>memo-resident mini-databases</strong>, in which an entire
serialized workspace — schema plus data — is stored as a memo payload, so a memo
becomes a self-contained object-oriented mini-database. A student's private work
could then live as a nested database inside a single memo, hydrated on demand
(memo bytes → DTSHEMA and data → virtual areas or VDISK), which aligns closely
with the Laboratory Campus teaching mission.</p>
<p>The proposal carries explicit hard constraints: memos stay <strong>payload-agnostic</strong>
(no privileged "workspace memo" type that would restrict other memo payloads);
the classic destructive <code>WORKSPACE OPEN</code> remains available <strong>with a warning</strong> for
existing scripts; and the work is <strong>fenced away from the AI-BBS agent-server
lane</strong>. Illustrated future effects — a DTSHEMA version bump with a per-area
<code>kind</code>, scoped <code>WORKSPACE SAVE</code> by named workspace, and the hydration path above —
are planning sketches only. The design whitepaper is authored in the proposing
agent's workspace and pending delivery into the local tree before it can be
linked here.</p>
