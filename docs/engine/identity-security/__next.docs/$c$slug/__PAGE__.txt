6:Tde6,<p>x64base now has a layered identity and authorization system. The <code>USER</code> command
is the administrative and diagnostic surface for members, authentication,
roles, permissions, grants, acting identity, persistence, and enforcement.</p>
<p>This is current development source and runtime evidence. The lane is not yet a
tagged-release claim; M4/M5/M6 promotion work remains open.</p>
<h2 id="the-model"><a class="no-underline" href="#the-model">The model</a></h2>

































<table><thead><tr><th>Layer</th><th>Responsibility</th></tr></thead><tbody><tr><td>Identity</td><td>Persist HUMAN, AI, and SERVICE members in the identity DBF store.</td></tr><tr><td>Authentication</td><td>Establish and clear login sessions; passwords serve human identities, while AI/service identities can use rotated tokens.</td></tr><tr><td>RBAC</td><td>Resolve roles, permissions, direct grants, authorization requests, deny precedence, and time-bounded decisions.</td></tr><tr><td>Acting identity</td><td>Track principal and acting member without treating impersonation as a permission grant.</td></tr><tr><td>Runtime policy</td><td>Enforce permission checks at owner administration, host shell, AI/tool, and SFTP chokepoints.</td></tr><tr><td>Degraded boot</td><td>Preserve a read-only identity view when the persistent store cannot safely open.</td></tr></tbody></table>
<p>Representative inspection and administration commands include:</p>
<pre><code class="language-text">USER WHOAMI
USER STORE
USER LIST
USER ROLES
USER PERMS
USER CAN &#x3C;permission.key> [FOR &#x3C;member.key>]
USER LOGIN &#x3C;member.key> [secret]
USER LOGOUT
USER REQUEST &#x3C;permission.key> FOR &#x3C;member.key> [reason]
USER GRANT &#x3C;permission.key> TO &#x3C;member.key> [HOURS n]
USER VERIFY [dir]
</code></pre>
<p>Mutating forms such as member admission/deletion, password or token rotation,
grant decisions, and persistent saves are owner- or authorization-gated. They
change identity metadata and session state, not user application tables.</p>
<h2 id="security-is-a-separate-compatibility-surface"><a class="no-underline" href="#security-is-a-separate-compatibility-surface"><code>SECURITY</code> is a separate compatibility surface</a></h2>
<p><code>SECURITY SHOW</code>, <code>SELFTEST</code>, and <code>RUNTIME</code> report policy and runtime diagnostics.
Its <code>SECURITY LOGIN &#x3C;DEVELOPER|TEACHER|STUDENT></code> form selects only a legacy
diagnostic role used by that command. It does <strong>not</strong> authenticate a <code>USER</code>
member, establish an RBAC session, or grant permissions.</p>
<p>Use <code>USER LOGIN</code>, <code>LOGOUT</code>, <code>WHOAMI</code>, and <code>CAN</code> for the authenticated model.
Keeping these surfaces separate prevents a diagnostic selector from being
mistaken for an authorization boundary.</p>
