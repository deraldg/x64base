6:T3229,<p>A <strong>workspace</strong> is the shape of a working session: which tables are open in
which work areas, which index containers are attached, which tag orders are
selected, what aliases they answer to, which relations are declared between
them, and -- since version 3 -- where every cursor sat and which area was
selected. It is the difference between "the data" and "how the data is
currently arranged for work."</p>
<blockquote>
<p><strong>Alpha development boundary.</strong> Saved workspaces and memo-to-RAM MINIDB
hydration are runtime-proven development capabilities. Concurrent, recursive
and nested workspace management is active early work; it is discussed here as
direction until its own runtime evidence and limits are recorded.</p>
</blockquote>
<p>Workspaces are ordinary text or ordinary table rows. There is nothing
proprietary in the middle.</p>
<h2 id="the-command-surface"><a class="no-underline" href="#the-command-surface">The command surface</a></h2>
<p><code>WORKSPACE SAVE &#x3C;name> [MEMO] [V3] [MINIDB]</code> and
<code>WORKSPACE LOAD &#x3C;name> [MEMO] [RAM]</code>. The trailing keywords are modifiers,
combinable in either order, and every one of them is opt-in -- the bare forms
behave exactly as they always have.</p>









































<table><thead><tr><th>Form</th><th>What it does</th></tr></thead><tbody><tr><td><code>WORKSPACE SAVE &#x3C;file></code></td><td>writes a <code>.dtschema</code> text snapshot (format version 2)</td></tr><tr><td><code>WORKSPACE SAVE &#x3C;file> V3</code></td><td>version 3: adds measured flavor, its own dbf/index/lmdb roots, and session state</td></tr><tr><td><code>WORKSPACE SAVE &#x3C;name> MEMO</code></td><td>stores the snapshot in a memo field of the <code>WORKSPACES</code> catalog instead of a file</td></tr><tr><td><code>WORKSPACE SAVE &#x3C;name> MEMO MINIDB</code></td><td>stores the snapshot <em>and every table and index byte</em> as one container (implies V3)</td></tr><tr><td><code>WORKSPACE LOAD &#x3C;file></code></td><td>restores from a text snapshot</td></tr><tr><td><code>WORKSPACE LOAD &#x3C;name> MEMO</code></td><td>restores from the catalog</td></tr><tr><td><code>WORKSPACE LOAD &#x3C;name> MEMO RAM</code></td><td>hydrates the tables into the RAM virtual disk, then restores against them</td></tr><tr><td><code>WORKSPACE CLOSE</code></td><td>closes areas and clears relations</td></tr></tbody></table>
<p>Two carriers, one format: the snapshot text is byte-identical whether it
lands in a file or a memo field, because there is one serializer and one
loader. A second writer would be a second truth, and the project has been
bitten by exactly that before -- a parallel snapshot writer once claimed the
same format version name for an incompatible layout, and reconciling it to a
name of its own is recorded doctrine rather than a quiet cleanup.</p>
<h3 id="version-3-and-why-version-2-stays"><a class="no-underline" href="#version-3-and-why-version-2-stays">Version 3, and why version 2 stays</a></h3>
<p>Version 3 is a superset: same body, extra declarative lines. Older readers
skip lines they do not recognize, so a v3 snapshot degrades rather than
breaks, and v2 remains the default so every proven path keeps working
untouched. What v3 adds:</p>
<ul>
<li><strong>Measured flavor</strong> -- read from the open tables at save time, never
declared by hand. Disagreement among areas is reported as mixed rather
than averaged away.</li>
<li><strong>Its own roots</strong> -- the snapshot records the directories its tables and
indexes live under, so a restore resolves against the <em>payload's</em> roots
rather than whatever environment happens to be set. The standing proof
deliberately points the engine at the wrong directories first; the
workspace still stands up.</li>
<li><strong>Session state</strong> -- each area's physical record position and the selected
area. On restore they are applied and then relations are refreshed, so
children re-slave to the restored parent positions.</li>
</ul>
<h3 id="the-catalog"><a class="no-underline" href="#the-catalog">The catalog</a></h3>
<p>Memo-carried workspaces live in <code>WORKSPACES</code>, a self-creating x64 table in
the workspaces root. Each row records a unique id, the name, the display
schema name, measured flavor, OS-compatibility claim, payload format,
size, the areas it opens, recursion-guard fields, the id of the row it
superseded, the author (a real member identity), the timestamp, and the
roots active at save. Those columns form the envelope. The <code>SNAPSHOT</code> memo
field carries the value: a posture for <code>DTSHEMA</code> rows, or the whole database
container for <code>MINIDB 1</code> rows. In the second case the row does not point to a
database elsewhere; the row contains its raw DBF, CDX and carried DTX members.
Saving again supersedes rather than overwrites, so the table keeps its own
history -- and that lineage chain is, in practice, a commit log.</p>
<p><code>WORKSPACES.dbf</code> is therefore heterogeneous by design: identity rows, posture
rows and whole-database rows share one queryable outer table. Calling it only
metadata misses the inversion that matters.</p>
<p>Every memo save is verified: the payload is read back through the token
stored <em>in the field</em> -- not the one held in memory -- and byte-compared. A
field-width truncation once slipped past a memory-side check; it cannot
again.</p>
<h2 id="multiple-workspaces-and-simultaneous-use"><a class="no-underline" href="#multiple-workspaces-and-simultaneous-use">Multiple workspaces and simultaneous use</a></h2>
<p>Here the documentation has to be careful, because the honest answer has three
parts.</p>
<p><strong>What is true today.</strong> Several workspaces can be open <strong>at once</strong>. Since
2026-08-26 both <code>WORKSPACE OPEN</code> and <code>WORKSPACE LOAD</code> are <strong>additive</strong>: a load
closes nothing, and a saved posture's area numbers are treated as <em>keys</em> rather
than engine addresses, so its tables are placed into the current workspace
wherever there is room. To get the old replacing behaviour you now compose it --
<code>WORKSPACE CLOSE ALL</code> then <code>WORKSPACE OPEN &#x3C;dir></code>.</p>
<p>This page said the opposite until 2026-09-02, and the engine's own
<code>WORKSPACE USAGE</code> text has carried the dated correction since 08-27. The
correction is recorded here rather than quietly swapped, because a reader who
built a habit on the old sentence should be able to see that it changed and
when.</p>
<p><strong>What that costs.</strong> Additive loading means a second <code>LOAD</code> adds to what you
have rather than replacing it, which is what makes two schemas side by side
possible -- and it means a careless load lands tables you did not expect. The
scoped forms exist for exactly that: <code>CLOSE</code> and <code>SAVE</code> act on one workspace by
default, with an explicit form for everywhere.</p>
<p><strong>Why it was not simply switched on.</strong> Co-residency was never a memory problem;
it is a <em>naming</em> problem. Four hazards were named here before any code was
committed to them, and they are worth keeping visible because three have since
closed:</p>
<ul>
<li><strong>Relation scope.</strong> <em>Closed 2026-08-23.</em> The relation store is partitioned by
workspace, so a refresh knows whose graph it belongs to. A follow-on hole --
the refresh <em>parent</em> still resolving unscoped -- closed 08-27.</li>
<li><strong>Work-area budget.</strong> <em>Closed.</em> Allocation is workspace-aware. Measured: one
workspace took areas 0-1, a second took the lowest free slot and grew
contiguously from there.</li>
<li><strong>Name resolution.</strong> <em>Half closed.</em> Within one workspace two areas can no
longer share a logical name: <code>USE</code> refuses an explicit alias already held, and
auto-renames a stem collision to <code>&#x3C;stem>2</code> and says so. The two resolvers that
used to disagree are now built on one primitive. <strong>Still open:</strong> <code>CREATE</code> will
open a second same-named table without renaming, and <code>SELECT &#x3C;name></code> is not
workspace-scoped. This remains the sharp one.</li>
<li><strong>RAM residency.</strong> <em>Still open.</em> Hydration flattens tables to filenames under
one virtual root, so two hydrated workspaces would both want the same
<code>STUDENTS.dbf</code> slot. A per-workspace subroot is still a decision, not a
feature.</li>
</ul>
<p>A fifth hazard was not on the original list and turned out to matter as much as
any of them:</p>
<ul>
<li><strong>Environment ownership.</strong> <em>Closed 2026-08-29.</em> The DBF, INDEXES and LMDB path
slots used to be global, and switching workspaces moved membership without
moving them -- so with two systems open, a table in one would resolve its
index container under the other. The slots are now stamped on the workspace and
restored on switch, with <code>SET PATH &#x3C;slot> &#x3C;value> IN &#x3C;ws></code> to bind another
workspace by name.</li>
</ul>
<p><strong>What sharing means.</strong> The RAM virtual disk is in-process. Another user, or
another process, cannot see your hydrated workspace at all -- so sharing is
necessarily an explicit act: write it back to disk, or send it. That is a
constraint, but a clarifying one, because it puts locking exactly where it
belongs -- at the moment work crosses back into shared storage, not around the
private work itself.</p>
<h3 id="nesting"><a class="no-underline" href="#nesting">Nesting</a></h3>
<p>A MINIDB is the portable database image: workspace posture plus member files in
one memo payload. Hydration produces a live workspace.</p>
<p>Nesting needed explicit <strong>depth, cycle, ownership, resolution and close-order</strong>
rules before it could be published. Four of those five now have answers:</p>
<ul>
<li><strong>Ownership.</strong> <code>WORKSPACE NEW &#x3C;name> UNDER &#x3C;parent></code> records the parent's
<em>durable</em> catalog id, never the session handle -- a handle does not survive the
process, and the durable id is what persistence means.</li>
<li><strong>Depth.</strong> Recorded as the parent's depth plus one, computed when the row is
written rather than asserted afterwards.</li>
<li><strong>Cycle.</strong> Refused at creation, alongside a refusal for a parent that does not
exist.</li>
<li><strong>Close order.</strong> <code>WORKSPACE DESTROY</code> retires only an empty, childless
workspace. A setting decides whether closing a workspace descends into nested
ones, and a skipped child is always reported rather than silently left behind.</li>
<li><strong>Resolution</strong> is the one still genuinely open -- see the name-resolution
hazard above.</li>
</ul>
<p>The governing rule is that <strong>containment is declared, never inferred.</strong> A
workspace with no recorded parent means exactly one thing: no container was
declared. A workspace whose intended parent has no durable identity is refused
at declaration rather than quietly recorded as a root -- because an intent
expressed as an absence cannot be told apart from a default.</p>
<p>One consequence reads as a limitation and is really the rule working: <strong>you
cannot currently nest under the default workspace</strong>, not because of any rule
about it, but because it has no durable catalog row, and a container that cannot
be named cannot be recorded. Give it one and nesting under it follows with no
change to the rules.</p>
<p><strong>Nested MINIDB is a different claim and is not made here.</strong> Workspace nesting
is declared and durable; a container whose <em>payload</em> holds another container
remains chartered and unexercised, with measured at-rest depth of one.</p>
