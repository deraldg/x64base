1c:T2a77,<h2 id="what-sqlsel-is"><a class="no-underline" href="#what-sqlsel-is">What SQLsel is</a></h2>
<p><code>SQLsel</code> is a set-oriented <code>SELECT</code> statement over an open work area. It is a
supported surface as of 2026-07-29.</p>
<pre><code class="language-text">SQLSEL SELECT &#x3C;col>[,&#x3C;col>...] FROM &#x3C;table>
       [WHERE &#x3C;predicate>] [ORDER BY &#x3C;field> [ASC|DESC]] [LIMIT &#x3C;n>]
SQLSEL SELECT * FROM &#x3C;table>
SQLSEL SELECT COUNT(*) FROM &#x3C;table> [WHERE &#x3C;predicate>]
</code></pre>
<p>It is deliberately <strong>statement-scoped</strong>. A statement names its own table, ignores
session filter and cursor state, restores every cursor it touches, and reads
committed table truth. Running one changes nothing about where you were.</p>
<h2 id="how-it-is-verified"><a class="no-underline" href="#how-it-is-verified">How it is verified</a></h2>
<p>Every result set is compared against an <strong>in-process SQLite oracle over identical
data in the same run</strong> - the same rows loaded into both engines, the same query
asked of both, the outputs compared row for row. That comparison is a registered
regression (<code>REGRESSION SQLSEL_SELECT_V1</code>), not a one-time exercise.</p>
<p>The regression also asserts the parts that are easy to get quietly wrong:</p>
<ul>
<li><strong><code>ORDER BY</code> sorts the full match set BEFORE <code>LIMIT</code> cuts it.</strong> <code>ORDER BY LNAME DESC LIMIT 2</code> returns the two highest rows, not the first two rows found.</li>
<li><strong>Cursor neutrality, proven by data</strong> - the cursor is parked on a known record
before the statement and checked after.</li>
<li><strong>Corrective errors, never silent zeros</strong> - an unopened table, an expression
where a column name belongs, a bad <code>LIMIT</code>, an unknown <code>ORDER BY</code> field, and
<code>ORDER BY</code> on <code>COUNT(*)</code> each report what is wrong.</li>
<li><strong><code>LIMIT</code> says what it withheld</strong>, and <code>ORDER BY</code> names its access path.</li>
</ul>
<h2 id="what-it-does-not-do"><a class="no-underline" href="#what-it-does-not-do">What it does not do</a></h2>





























<table><thead><tr><th>Not supported</th><th>Status</th></tr></thead><tbody><tr><td><code>JOIN</code> (any form)</td><td>Planned. See the note on relational methodology below</td></tr><tr><td><code>GROUP BY</code> / <code>HAVING</code></td><td>Not implemented anywhere in the engine</td></tr><tr><td>Expression projection (<code>UPPER(name)</code> in the select list)</td><td>v1 accepts bare column names only</td></tr><tr><td><code>INSERT</code> / <code>UPDATE</code> / <code>DELETE</code> as SQL syntax</td><td>The engine mutates through <code>APPEND</code>, <code>REPLACE</code>, <code>DELETE</code>; SQL DML is planned</td></tr><tr><td>Bare <code>SELECT ...</code> without the <code>SQLSEL</code> prefix</td><td>Planned convenience layer</td></tr></tbody></table>
<p>The table must already be open (<code>USE &#x3C;table></code>). SQLsel reads open work areas; it
does not open files for you.</p>
<h2 id="the-sql-command-family"><a class="no-underline" href="#the-sql-command-family">The SQL command family</a></h2>
<p>Four commands begin with <code>SQL</code> and do different things. The names invite
confusion, so the boundary is stated in each command's own contract, in its
runtime <code>USAGE</code> output, and in <code>HELP</code>.</p>

























<table><thead><tr><th>Command</th><th>What it is</th></tr></thead><tbody><tr><td><code>SQLSEL</code></td><td><strong>SQLsel.</strong> The <code>SELECT</code> statement surface, over a named table that is already open</td></tr><tr><td><code>SQL</code></td><td>A <strong>predicate scan or count over the CURRENT work area</strong>. It does not execute SQL statements; the name is historical</td></tr><tr><td><code>SQLITE</code></td><td>The <strong>bridge to an actual SQLite database</strong></td></tr><tr><td><code>SQLVER</code></td><td>Reports SQLite availability and version</td></tr></tbody></table>
<p>Two consequences worth knowing.</p>
<p><code>SQL SELECT * FROM STUDENTS</code> does not run a query. Until 2026-07-29 that line was
parsed as a <em>predicate</em> and returned a confusing failure; it now detects the
leading <code>SELECT</code> and redirects to <code>SQLSEL</code> with the real grammar rather than
answering a question nobody asked.</p>
<p><code>SQL COUNT FOR &#x3C;expr></code> and <code>SQLSEL COUNT FOR &#x3C;expr></code> are <strong>equivalent</strong>. SQLsel
kept the predicate-scan form when it gained statements, so the overlap is
deliberate rather than accidental.</p>
<h2 id="reltalk-and-sqlsel-two-ways-to-reach-connected-data"><a class="no-underline" href="#reltalk-and-sqlsel-two-ways-to-reach-connected-data">RelTalk and SQLsel: two ways to reach connected data</a></h2>
<p>These are two different things that are related. One is old, one is new, and the
new one does not replace the old one. Both are supported surfaces.</p>








































<table><thead><tr><th></th><th><strong>RelTalk</strong> (old)</th><th><strong>SQLsel</strong> (new)</th></tr></thead><tbody><tr><td>Lineage</td><td>Inherited from the xBase / FoxPro line, itself descended from navigational database practice</td><td>Relational algebra, the SQL tradition</td></tr><tr><td>How you ask</td><td><strong>Navigate</strong> - declare the links, then follow them</td><td><strong>Declare</strong> - describe the result, let the engine find it</td></tr><tr><td>Setup</td><td><code>REL ADD</code> wires parent to child on a key, ahead of time</td><td>Nothing declared; match any two columns on demand</td></tr><tr><td>Shape</td><td>Walks a configured path in a direction, emitting one row per leaf combination</td><td>Matches two row sets</td></tr><tr><td>Commands</td><td><code>REL ADD</code>, <code>REL JOIN</code>, <code>REL ENUM</code>, <code>ERSATZ</code>, <code>SET RELATION</code></td><td><code>SQLSEL SELECT</code></td></tr><tr><td>Today</td><td>Supported</td><td><code>SELECT</code> supported; <code>JOIN</code> planned</td></tr></tbody></table>
<p>The distinction is the navigational/relational one. The navigational model asks
"where do I go from here?" - you position on a parent record and follow declared
links to its children, as CODASYL sets and xBase <code>SET RELATION</code> did. The
relational model asks "which rows satisfy this?" - you state a condition and
receive a set, with no notion of where you were positioned.</p>
<p>Both can be run against the same tables in the same session, which makes the
difference observable rather than described. RelTalk is therefore not deprecated
by the arrival of SQL; the two answer different questions.</p>
<p><strong>They are related</strong> in that both ultimately read the same DBF tables through the
same indexes, and both can produce join-shaped rows. They are <strong>not the same
thing</strong>, and this documentation will not describe one as the other. When SQL
joins arrive they will be built as their own set-matching path rather than
compiled down to declared traversal, specifically so the distinction survives
contact with the implementation.</p>
<p>See <a href="/docs/talk-family/reltalk">RelTalk</a> for the relation-graph surface in full.</p>
<p>There is one further honest wrinkle: SQL <code>LEFT JOIN</code> fills unmatched columns with
<code>NULL</code>, and <strong>x64base has no NULL</strong> - a blank is a value. Unmatched rows will
therefore carry an explicit marker rather than a blank that could be mistaken for
real data, and the count of extended rows will be reported.</p>
<h2 id="sql-conformance-map"><a class="no-underline" href="#sql-conformance-map">SQL conformance map</a></h2>
<p>The engine ships a machine-readable answer to "I know this SQL construct - does
x64base do it, and how?" It lives in <code>include/sql_ref.hpp</code>, alongside the SQL
reference itself, and covers equivalences as well as absences:</p>
<ul>
<li><code>SELECT</code> basic and <code>COUNT(*)</code> - <strong>supported</strong>, SQLsel</li>
<li><code>CREATE TABLE</code> - <strong>equivalent, different syntax</strong> (<code>CREATE X64</code>, <code>DDL CREATE DBF</code>);
xBase types are C/N/D/L/M, and there is no <code>AUTOINCREMENT</code></li>
<li><code>CREATE INDEX</code> - <strong>equivalent, two steps</strong> (<code>INDEX ON ... TAG</code>, then <code>BUILDLMDB</code>)</li>
<li><code>INSERT</code> - <strong>equivalent, two steps</strong> (<code>APPEND</code>, then <code>REPLACE</code>); cursor-oriented</li>
<li><code>DELETE</code> - <strong>equivalent with a real difference</strong>: <code>DELETE</code> marks, <code>RECALL</code>
un-marks, <code>PACK</code> removes. Closer to a soft delete than SQL's</li>
<li><code>BEGIN TRANSACTION</code> / <code>COMMIT</code> / <code>ROLLBACK</code> - <strong>supported</strong>, via <code>TABLE BUFFER ON</code>,
<code>COMMIT</code>, <code>ROLLBACK</code>, with a write-ahead journal fsynced before any DBF byte moves</li>
<li><code>EXPLAIN QUERY PLAN</code> - <strong>partial</strong>: there is no planner to explain, because
access paths are chosen by the operator, not a cost model. What exists is
reporting - SQLsel names its access path, and <code>GPS</code> shows physical record
against logical row</li>
<li><code>GROUP BY</code>, <code>JOIN</code> - <strong>not supported</strong>, as above</li>
</ul>
<p>Entries nobody has verified yet are left <strong>empty on purpose</strong>. Empty means
unchecked, not absent - guessing would defeat the point of the map. A gate
(<code>sql_conformance_gate.py</code>) checks that every command the map points at is a
command the shell actually registers.</p>
<p><strong>The map describes, it does not promise.</strong> It exists to answer "does x64base do
this, and how?" for someone who already knows SQL, and to show where the gaps
are. It is not a compatibility claim: x64base does not offer to run SQLite or
MSSQL work, and an "equivalent" row means the engine achieves the same intent by
different syntax with its own semantics - <code>DELETE</code> marks rather than removes,
there is no <code>NULL</code>, and types are C/N/D/L/M rather than SQL types. Read those
rows as translation guidance, not as portability.</p>
<h2 id="checking-these-claims"><a class="no-underline" href="#checking-these-claims">Checking these claims</a></h2>
<p>Each claim on this page is intended to be verifiable by running something:</p>
<ul>
<li>the <code>SELECT</code> behavior, via <code>REGRESSION SQLSEL_SELECT_V1</code></li>
<li>the conformance map's command references, via <code>sql_conformance_gate.py</code></li>
<li>the command's own grammar, via <code>SQLSEL USAGE</code></li>
</ul>
