<h3 id="what-classic-x32-support-means-here-exactly"><a class="no-underline" href="#what-classic-x32-support-means-here-exactly">What classic x32 support means here, exactly</a></h3>
<p>Classic 32-bit support is <strong>deliberately limited in scope</strong>, and the scope is
worth stating precisely so nobody plans around a promise that was never made.
What is supported is <strong>tables, memos, and indexes</strong> -- and specifically the
<strong>house memos and house indexes we provide for v32</strong>:</p>





















<table><thead><tr><th>In scope for x32</th><th>Detail</th></tr></thead><tbody><tr><td>Tables</td><td>classic DBF table reading, writing, structure, cursor and record work</td></tr><tr><td>House memos</td><td>the memo carriers this project implements and maintains</td></tr><tr><td>House indexes</td><td>the INX and CNX containers this project implements and maintains, including realtime CNX order maintenance</td></tr></tbody></table>
<p>That is the whole claim. This project is not a Clipper, dBASE, or FoxPro
compatibility platform, does not aim to reproduce a legacy application
runtime, and does not chase every historical index or memo variant produced
by three decades of vendors. The x32 lane exists because teaching a database
engine honestly means showing the classic generation beside the new one -- not
because this is a migration target.</p>
<p><strong>If you need broader classic coverage, other platforms exist and are better
suited.</strong> Harbour, xHarbour, Alaska Xbase++, XSharp, and the commercial
dBASE/DBF tool families all carry far deeper legacy compatibility, and the
<a href="/docs/engine/ecosystem-feature-comparison">ecosystem comparison</a> names them
with links. Choosing one of those over this project for legacy work is the
correct decision, and saying so costs this project nothing.</p>
