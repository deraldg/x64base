6:T2e35,<p>DotTalk++ / x64base is a <strong>DBMS</strong> — it owns its storage, its indexes, its
locking and its recovery — and it is also an <strong>RDBMS</strong>: it stores relations,
declares relationships between them, <strong>enforces a declared primary key on
write</strong>, and answers questions with relational algebra rather than only with
cursor navigation.</p>
<p>Keys came last and are stated first here because they are the relational
primitive. A column designated <code>PRIMARY</code> is generated on <code>APPEND</code>, held
against reuse until <code>PACK</code>, refused on rewrite, and stamped into the table's
own metadata so a fresh process still refuses. That is a real key, not a
convention — and it landed on 2026-09-07, which is recent enough that a
reader who last looked earlier would reasonably still believe otherwise.</p>
<p>Both halves are stated here with their evidence, and so is the boundary. A
system that claims the word "relational" without saying where it stops is
selling, not documenting.</p>

<h2 id="the-relational-half"><a class="no-underline" href="#the-relational-half">The relational half</a></h2>
<p>A relation here is an ordinary table, and relationships between them are
expressed <strong>two different ways on purpose</strong>.</p>
<p><strong>Declared, navigational — RelTalk.</strong> <code>REL ADD parent child ON key</code> establishes an
edge in advance; <code>REL JOIN</code> walks it and emits one tuple per leaf combination.
The question it answers is <em>"where do I go from here?"</em>. See
<a href="/docs/talk-family/reltalk">RelTalk</a>.</p>
<p><strong>Undeclared, set-oriented — SQLsel.</strong> A <code>SQLSEL</code> statement names its own tables
and <code>ON</code> columns, reads no <code>REL</code> or <code>SET RELATION</code> state at all, and answers
<em>"which rows satisfy this?"</em>. It carries the operators a relational engine is
expected to have:</p>
<ul>
<li>selection and projection, <code>DISTINCT</code>, <code>LIMIT</code>, and <code>ORDER BY</code> with
independent per-column directions</li>
<li><code>INNER</code>, <code>LEFT</code>, <code>RIGHT</code>, <code>FULL</code> and <code>CROSS</code> joins; <strong>self-joins through
aliases</strong> over a single physical table; <strong>composite boolean <code>ON</code></strong>; and
three-table <code>INNER</code>/<code>LEFT</code> chains</li>
<li><code>COUNT</code>, <code>SUM</code>, <code>AVG</code>, <code>MIN</code>, <code>MAX</code> with <code>GROUP BY</code> and <code>HAVING</code></li>
<li><code>UNION</code>, <code>UNION ALL</code>, <code>INTERSECT</code>, <code>EXCEPT</code></li>
<li>subqueries: scalar, <code>IN</code>, <code>NOT IN</code>, <code>EXISTS</code> and <code>NOT EXISTS</code>, both
<strong>uncorrelated and correlated</strong> — including double-<code>NOT EXISTS</code>
<strong>relational division</strong>, which is the "for all" question and the operator
most often missing from things that call themselves relational</li>
<li>expression projection, so <code>TRIM(LNAME)</code> is a column, over an AST shared
between projection and predicate</li>
<li><code>INSERT</code>, <code>UPDATE</code>, <code>DELETE</code> with single-table transactions</li>
<li><strong>workspace-scoped name resolution</strong>: two open workspaces may hold the same
table name with different rows, and a statement resolves within the current
workspace rather than to the engine's lowest matching slot</li>
<li><strong>committed-read isolation</strong>: inside an explicit transaction <code>SQLSEL</code> reads
committed table truth while <code>TUPLE</code> previews the dirty row buffer, so the two
surfaces disagree on purpose and each says which it is showing</li>
<li><strong>typed empty results</strong>: a join whose right side matches nothing preserves the
column schema rather than collapsing to no shape at all</li>
</ul>
<p>Neither of those two query surfaces replaces the other. One follows a
structure you asserted about your data; the other asks a question that
stands on its own.</p>
<p><strong>Declared, enforced — a primary key.</strong> As of 2026-09-07 a column can be
designated with <code>SET UNIQUE FIELD &#x3C;field> PRIMARY</code>, and the designation does
three separate things. It <strong>generates</strong>: an <code>APPEND</code> into a blank key mints
<code>max+1</code> inside the writer's table lock, so two writers cannot mint the same
value. It <strong>reserves</strong>: a deleted row keeps its key until <code>PACK</code>, because
<code>RECALL</code> can bring that row back and a reissued key would collide with it. And
it <strong>refuses</strong>: a write that would change a minted key is rejected rather than
quietly accepted.</p>
<p>It is real schema, not session state. The designation is stamped into the x64
field metadata as <code>X64_FIELD_FLAG_PRIMARY</code>, so a fresh process reopens the table
and still refuses — which was not true until 2026-09-07, when the designation
lived only in a process-local map that a restart discarded. Two consequences
follow and both matter to a reader: it is <strong>x64-flavour-scoped</strong>, because the
flag has nowhere to live in a classic or VFP descriptor, and a reader that does
not know the flag reads zero and enforces nothing, in silence.</p>
<p>The policy in full — what each behaviour is, which spec proves it, why two of
that spec's arms are expected red, and the write paths enforcement does not yet
reach — is on <a href="/docs/engine/primary-keys">Primary Keys</a>.</p>
<h2 id="how-the-relational-claim-is-checked"><a class="no-underline" href="#how-the-relational-claim-is-checked">How the relational claim is checked</a></h2>
<p>Every SQLsel regression compares its result sets against an <strong>in-process SQLite
oracle over identical data in the same run</strong> — not against a recorded
expectation. That distinction is the point: a stored expectation only proves our
reader agrees with our writer, and a shared misunderstanding passes. An
independent engine answering the same question over the same rows does not.</p>
<p>Six of those specs run on every <code>REGRESSION ALL</code>; seven more are explicit-run.
See <a href="/docs/engine/regression-and-proof-testing">Regression and Proof Testing</a> and
<a href="/docs/engine/sqlsel-and-sql-conformance">SQLsel and SQL Conformance</a>.</p>
<p>The key claims are checked differently, and the difference is worth stating.
There is no oracle for "was this write refused" — SQLite would simply have
refused it too. So <code>PKPOLICY</code> asks the answerable question instead: every arm
reads a FIELD VALUE back after the attempt. If the cell holds its original
value the write was refused; if it holds the new one it was not. Console text
is never the evidence. Five arms cover five different doors into a field write
— native <code>REPLACE</code>, <code>SQLSEL INSERT</code>, <code>SQLSEL UPDATE</code>, and the two legacy bare
<code>INSERT</code>/<code>UPDATE</code> verbs, which are different files reached by a different
registration — because a fix wired into one is not evidence about another.</p>
<p>Persistence needs a second process, which no single script can provide, so
<code>PKDURABLE</code> is a two-run harness: one process declares and writes, another
starts cold and must still refuse. It is the only spec in the tree that can say
a designation survived a restart.</p>
<h2 id="where-it-stops-stated-plainly"><a class="no-underline" href="#where-it-stops-stated-plainly">Where it stops, stated plainly</a></h2>
<blockquote>
<p><strong>Referential integrity is not enforced on write.</strong> Relations are declared for
<em>traversal</em>, not as constraints. Deleting a parent does not refuse, cascade, or
null out its children. This is the sharpest gap between x64base and a
constraint-enforcing RDBMS, and it is a design position rather than an
oversight — but a reader should not infer enforcement from the word
"relational".</p>
<p>This gap got <strong>sharper</strong> in 2026-09, not softer. A declared primary key is
now refused on write, so the engine demonstrably can decline a write on
integrity grounds — it simply does not decline this one. "Not built yet" and
"built elsewhere and deliberately not here" are different statements, and
this is now the second.</p>
</blockquote>
<p>Also absent, and each refused rather than silently approximated:</p>
<ul>
<li>
<p><strong>Universal primary-key enforcement.</strong> What is proven is five write paths
— the ones <code>PKPOLICY</code> asserts. A static gate counts <strong>22 direct field-write
call sites across 15 files</strong> that do not go through the funnel, and
<code>CALCWRITE</code>, browse and record-view editing, <code>COPY</code>, <code>SORT</code> and <code>IMPORTSQL</code>
are unasserted. Five of five is the arms that exist, not a key that is
enforced everywhere; closing that is a static-analysis job, because no
runtime marker can enumerate a call site. See
<a href="/docs/engine/primary-keys">Primary Keys</a>.</p>
</li>
<li>
<p><strong>Cross-table atomic commit.</strong> An explicit transaction accepts one target table.</p>
</li>
<li>
<p><strong>Stored <code>NULL</code> through DML.</strong> <code>SQLSEL INSERT</code>/<code>UPDATE</code> refuse a null rather
than coercing a blank. Stored nulls themselves <em>do</em> exist — VFP-flavour tables
carry a real <code>_NullFlags</code> bit, byte-verified against files Visual FoxPro wrote
— but the DML path does not write one.</p>
</li>
<li>
<p><strong>Subqueries over a joined outer scope.</strong></p>
</li>
<li>
<p><strong>The bare <code>SELECT ...</code> form</strong> without the <code>SQLSEL</code> verb. xBase already spends
<code>SELECT</code> on <code>SELECT &#x3C;area></code>, which switches the active work area rather than
querying anything, so the two senses collide on the same word. <code>SQLSEL</code> is
the disambiguating verb; a leading <code>SELECT</code> after it parses but is redundant.</p>
</li>
<li>
<p><strong>Memo-field DML.</strong></p>
</li>
</ul>
