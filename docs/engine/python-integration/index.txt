19:T1b7b,<p>Python work in the x64base ecosystem is not one product. It currently has three
related but distinct layers:</p>

























<table><thead><tr><th>Surface</th><th>Current role</th><th>Status</th></tr></thead><tbody><tr><td><code>pydottalk</code></td><td>Optional native Python binding over selected x64base <code>DbArea</code>, record, field, memo-read, and physical CRUD operations</td><td>Active integration; read and disposable-copy CRUD smoke paths exist</td></tr><tr><td><code>pydottalk_api</code></td><td>Local FastAPI bridge used by pycrud for schema, fixtures, header metadata, table readback, and CRUD requests</td><td>Prototype; currently backed by SQLAlchemy and SQLite by default</td></tr><tr><td><code>pycrud</code></td><td>Python/Tk CRUD, relational, import/export, and metadata teaching surface launched from the Laboratory Campus portal</td><td>Prototype campus companion app</td></tr></tbody></table>
<p>These layers should be discussed together because they form a useful path from
native engine access to API experiments and visible teaching tools. They should
not be collapsed into one implementation.</p>
<h2 id="pydottalk-native-engine-access"><a class="no-underline" href="#pydottalk-native-engine-access">pydottalk: native engine access</a></h2>
<p>The optional pybind11 module is built with <code>BUILD_PYDOTTALK</code>. Current source
identifies the module as <code>pydottalk 0.4.0</code>; that is a source version, not a claim
that a public wheel or stable ABI has been released.</p>
<p>The binding currently exposes selected <code>DbArea</code> behavior:</p>
<ul>
<li>open and close a table.</li>
<li>inspect open state, filename, logical name, DBF directory, version byte, table
flags, area kind, record length, field count, and field definitions.</li>
<li>navigate with top, bottom, goto, and skip while inspecting BOF, EOF, record
number, and record count.</li>
<li>read the current record, scan records, and address fields by index or name.</li>
<li>append a blank record, set fields, write the current record, and mark a record
deleted.</li>
<li>inspect memo metadata and read memo text where supported.</li>
</ul>
<p>Current tests cover a read-only DBF path and physical CRUD against a disposable
copy. Python access to every DotTalk++ command, workspace operation, relation
service, index semantic, or memo mutation is not implied.</p>
<h2 id="pydottalk_api-local-http-bridge"><a class="no-underline" href="#pydottalk_api-local-http-bridge">pydottalk_api: local HTTP bridge</a></h2>
<p><code>pydottalk_api</code> gives pycrud a small local FastAPI boundary. Its current
implementation uses SQLAlchemy with SQLite as the default store. It exposes
status, schema, fixtures, xBase-flavored header metadata, table display and
seek, session lifecycle, and bounded replace, append, and delete operations.</p>
<p>Despite the similar name, this bridge does not currently put the native
<code>pydottalk</code> module behind HTTP. Converging those two surfaces is a development
possibility, not current architecture.</p>
<h2 id="pycrud-visible-database-literacy"><a class="no-underline" href="#pycrud-visible-database-literacy">pycrud: visible database literacy</a></h2>
<p>pycrud is an independent companion application, not the DotTalk++ engine. Its
Python/Tk interface makes several database ideas inspectable:</p>
<ul>
<li>CRUD forms and table grids.</li>
<li>SQLite by default, with optional MySQL and SQL Server connections.</li>
<li>SQL console and relational select, project, and join exercises.</li>
<li>CSV import, text/CSV preview, and JSON or xBase-flavored metadata export.</li>
<li>a constrained formula evaluator.</li>
<li>optional communication with the local <code>pydottalk_api</code> bridge.</li>
</ul>
<p>This makes pycrud useful in the Laboratory Campus as a comparison and literacy
lab: learners can see GUI, SQL, metadata, and record-oriented views without
misidentifying the app as the engine itself.</p>
<h2 id="possibilities-opened-by-these-surfaces"><a class="no-underline" href="#possibilities-opened-by-these-surfaces">Possibilities opened by these surfaces</a></h2>
<p>The existing pieces support several credible development directions:</p>
<ul>
<li><strong>Python notebooks and repeatable labs</strong> - inspect real DBF structures and
records, capture outputs, and connect experiments to SelfDoc evidence.</li>
<li><strong>Disposable mutation laboratories</strong> - teach append, replace, delete, stale
state, validation, and recovery against controlled table copies.</li>
<li><strong>Model comparison</strong> - place SQL tables, xBase work areas, records, cursors,
and metadata side by side in one lesson.</li>
<li><strong>Schema and header visualization</strong> - turn field definitions, DBF headers,
memo references, and table flags into inspectable diagrams and GUI panels.</li>
<li><strong>API-driven frontends and tests</strong> - use a bounded local service for browser,
GUI, automation, and contract-testing experiments.</li>
<li><strong>Conversion and migration tools</strong> - reuse native table inspection in
DB_Converter-style import, validation, and readback workflows.</li>
<li><strong>Shared GUI services</strong> - gradually move pycrud and other frontends toward
the Open GUI API instead of duplicating table behavior.</li>
<li><strong>Cross-platform Python packaging</strong> - create ABI-matched build profiles and,
after repeatable verification, platform-specific wheels.</li>
<li><strong>Deeper engine exposure</strong> - add index/order/seek, relation traversal,
workspace, memo-write, and diagnostic services only as their contracts and
proof become ready.</li>
</ul>
<p>These are possibilities, not blanket completion claims. The strongest near-term
opportunity is a clean teaching chain:</p>
<pre><code class="language-text">x64base engine
    -> pydottalk native binding
        -> Python inspection, tests, conversion, and notebooks

pycrud teaching app
    -> pydottalk_api local bridge
        -> SQLAlchemy / SQLite prototype data services

future reviewed bridge
    -> shared engine and GUI contracts
</code></pre>
<h2 id="boundaries-that-protect-accuracy"><a class="no-underline" href="#boundaries-that-protect-accuracy">Boundaries that protect accuracy</a></h2>
<ul>
<li><code>pydottalk</code> is not the DotTalk++ command shell.</li>
<li><code>pydottalk_api</code> is not currently the native binding exposed as HTTP.</li>
<li>pycrud is a Laboratory Campus companion tool, not x64base itself.</li>
<li>a source module and local smoke tests do not establish a public package,
stable ABI, or support guarantee.</li>
<li>Python capabilities should be promoted only when their source, ABI, tests,
and representative runtime evidence agree.</li>
</ul>
