## The stale-binary red -- diagnosed, predicted, and RESOLVED

**Outcome first: the rebuild fixed it. WB_T1..WB_T6 are `.T.` on Windows.**
The section is kept in full because the prediction was falsifiable and held,
and because the handoff defect that caused it is the durable lesson.

The maintainer re-ran the spec on Windows immediately after the commit and
WB_T5/WB_T6 did NOT print. They emitted:

```text
FORMULA error: scalar evaluation failed
FORMULA error: scalar evaluation failed
```

**Diagnosis, measured not inferred.** The staged runtime exe does not contain
the change:

```text
dottalkpp/bin/dottalkpp.exe       no FILE() string   built 2026-08-12T16:12:47Z
build/src/Release/dottalkpp.exe   no FILE() string   built 2026-08-12T16:12:47Z
src/cli/expr/function_catalog.cpp                   edited 2026-08-12T16:56:25Z
src/cli/expr/fn_string.cpp                          edited 2026-08-12T17:42:57Z
```

The MSVC build predates the `FILE()` addition by ~44 minutes. With no `FILE`
in the builtin tables the call fails function lookup, falls out of the
rhs_eval leg, and the expression never evaluates -- so the marker errors rather
than reading `.F.`. The engine is not implicated; the binary is.

Independent agreement from the house's own gate in the same commit run:
`FN_COVERAGE ... FILE`, with `IMPLEMENTED(fn specs) 75` against
`CATALOG(SYSFUNC) 74` -- source has the function, the generated catalog does
not yet. Two instruments, same conclusion.

This is `AI_README.md`'s documented trap ("`ninja: no work to do` is not proof
your change is in the binary") arriving from the other direction, and the
`datarun.ps1` staleness warning in `CLAUDE.md` existing for exactly this.

**The handoff defect is the agent's.** The proof was performed on a Linux
build and the closeout said so, but the agent handed the maintainer a re-run
without stating that the Windows exe MUST be rebuilt first because `FILE()` was
new. A proof that is platform-scoped must carry its platform precondition into
the handoff, not only into the record. Corrective sequence issued:
`cmake --build D:\code\ccode\build --target dottalkpp --config Release`, then
re-run, then stage.

**Confirmed by re-run.** `cmake --build ... --target dottalkpp --config Release`
then `datarun.ps1 -CommandLines 'REGRESSION RUN WORKSPACE_WRITEBACK'`: all six
markers `.T.`, build stamp `dottalk++ v0.6 (2026-08-12, b3f64828 dirty)
(Aug 12 2026 10:56:44)`. The rebuild was the ONLY variable changed between the
red and the green, so the diagnosis is confirmed rather than merely plausible.

The diagnostic itself was proven both ways before being trusted, per "a checker
is unproven until you have seen it FAIL": the binary grep returned 0 on the
stale MSVC exe and 1 on a binary known to contain the function. It discriminates.

Windows measures, recorded because they are new: hydrate 27 files / 104411 B /
68.8906 ms (zero disk reads); writeback 15 files / 95579 B / 57.4753 ms;
manifest 13 declared, all present; teardown removed 16 entries. The 27-vs-15
gap is the documented index behavior (index FILES derived, the CHOICE travels
in the posture), not a shortfall.
