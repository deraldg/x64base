## Purpose

Decide whether x64base should implement traditional x32/xBase compatibility
beyond DBF-shaped table output.

Current truth: x64base can write classic DBF-shaped output flavors through
`xbase::dbf_create`, and COPY can logically convert records into those shapes.
That does not mean the runtime supports traditional xBase index or memo
ecosystems. The supported local indexing lane is x64base CNX. Memo support is
stub/limited unless separately proven.

This lane exists so future COPY, DDL, AUTODBF, and migration work can say
exactly what x32 means: either DBF-shaped interchange only, or a deliberate
compatibility project with explicit cost, proof, and maintenance burden.

## Decision Question

Do we want to bother with traditional x32/xBase support?

Short answer: probably not as a core runtime priority. It may be worth a narrow
read/import/export compatibility layer if a real dataset, customer workflow, or
LabTalk lesson needs it.

## What Traditional Support Would Mean

Traditional support is more than writing a `.dbf` header:

- index file compatibility such as `.ndx`, `.mdx`, `.cdx`, or FoxPro-style tag
  behavior;
- memo file compatibility such as `.dbt` and `.fpt`, including block size,
  pointer encoding, deleted memo behavior, and corruption handling;
- code page, date, numeric, logical, null, and field-name compatibility;
- lock/concurrency semantics for old tooling;
- repair and inspection tooling for partial or damaged legacy file sets;
- regression fixtures from real legacy files, not only files generated by
  x64base itself.

## Pros

- Better import/export story for historical xBase datasets.
- Stronger LabTalk teaching value: students can see the difference between
  DBF-shaped output, x64base CNX, and actual legacy file ecosystems.
- Easier interop with old FoxPro/dBASE/Clipper tools where that matters.
- Cleaner COPY and DDL documentation because compatibility levels can be named
  instead of implied.
- Could turn x64base into a better preservation bridge for real legacy archives.

## Cons

- High maintenance cost for formats that are old, irregular, and dialect-heavy.
- Risk of misleading users: a partial `.cdx` or `.dbt` implementation can be
  worse than no compatibility claim.
- It competes with x64base's own CNX/index direction and modern schema sidecars.
- Real proof requires legacy fixtures, external tool readback, corruption cases,
  and dialect matrices.
- Memo compatibility is especially risky because pointer/block behavior and
  damaged-file recovery vary by dialect.
- Traditional write support could create files other tools partially accept and
  later corrupt, which raises the proof bar.

## Recommended Position

Keep the core runtime honest:

1. `MSDOS`/`DBASE`, `FOX26`/`FOXPRO`, and `VFP` output flavors mean DBF-shaped
   table output unless this lane proves more.
2. Indexing for current x64base workflows remains CNX unless a traditional
   index compatibility milestone is explicitly accepted.
3. Memo behavior remains stub/limited unless a traditional memo milestone is
   explicitly accepted.
4. COPY/DDL/AUTODBF should warn or document when a requested x32-style output
   cannot carry traditional index/memo compatibility.

## Possible Milestones

M0 - Inventory and dialect boundary:
- Identify which dialects matter: dBASE III/IV, FoxPro 2.x, Visual FoxPro,
  Clipper, or read-only preservation cases.
- Collect real fixture files with DBF plus any index/memo companions.
- Decide read-only, write-only, import/export, or full round-trip scope.

M1 - Compatibility labels:
- Add runtime/help wording that distinguishes DBF-shaped output, CNX-indexed
  x64base output, and traditional xBase compatibility.
- Ensure COPY, DDL, and AUTODBF use the same compatibility vocabulary.

M2 - Read-only preservation bridge:
- Inspect and import legacy DBF plus memo/index metadata without claiming that
  x64base can maintain those files natively.
- Preserve sidecar evidence and loss reports.

M3 - Memo decision:
- Either keep memo stub/limited and document it, or implement a proven `.dbt`
  and/or `.fpt` reader/writer with external-tool readback.

M4 - Index decision:
- Either keep CNX as the only supported index lane, or implement a proven
  traditional index read/write subset with external-tool readback.

M5 - Round-trip proof:
- Prove compatibility against external legacy tooling and real fixtures, with
  loss reports for unsupported features.

## Link Back To COPY PDLC

`DDL_SCHEMA_PDLC_LANE_V1.md` R1 owns the near-term COPY repair:

- restore source cursor after logical `COPY AS`;
- keep converted output data-only unless indexes are explicitly requested;
- warn/document that x32-style output does not imply traditional index/memo
  support.

This lane owns the separate strategic question: whether that warning should
remain permanent doctrine or become a roadmap to real traditional xBase
compatibility.
