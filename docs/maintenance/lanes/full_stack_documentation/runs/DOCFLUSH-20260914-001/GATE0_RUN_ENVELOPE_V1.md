**COMMITTED 2026-09-14 as `b6dabae63`** -- "selfdoc: one contract family in the
store, and a reader that reads all of it". Five files: the four above plus
`TIER0_STATE.md`, regenerated by the `tier0-refresh` hook and declared as riding

PASS, manual-link-integrity 164/164, AIF and R-number collision gates PASS.

**THE HALF OF THE BLOCKER THAT REMAINS IS AN ORDERING PROBLEM, and it is
structural rather than a mistake.** The store files are THEMSELVES TRACKED, so a
store rebuild dirties the worktree by definition. An exe built from a clean tree
and an uncommitted store cannot coexist. The sequence that resolves it:

    1. git checkout -- dottalkpp/data/help     (safe: regenerable, baseline above)
    2. .\build.ps1                             -> expect b6dabae63 dirty=0
    3. .\datarun -> CMDHELP BUILD LEGACY, then CMDHELP BUILD . d:\code\ccode\src
    4. commit the store                        -> binding closed

Step 1 touches files owned by a CONCURRENT SESSION. The modified content is this
session's own rebuild output and regenerates in seconds, so the revert is
believed safe -- but it is the owner's call, not the steward's.

Step 2 also settles whether any of this is needed: if the `dirty` flag ignores
data files, `dirty=0` will already be true and steps 1 and 4 collapse into
"rebuild the store and commit it".

## AN UNRECONCILED COUNT, named before anyone quotes it

Two instruments measured the contract-bearing population on 2026-09-14 and did
not agree, and neither is known to be wrong:

    source_census.py        commands (@usage)           232 FILES
    contract_inventory.py   mined contracts from        208 FILES
                            distinct commands            223
                            contract BLOCKS              241

A 24-file gap between the two file counts. Candidate explanations exist -- the
16 files carrying `@dottalk.usage.voluntary` (which the store's miner does not
match and this tool lists separately), and the 9 plain-form blocks in
doc-tooling files that declare no `command:` -- but 16 + 9 is 25, not 24, so
the arithmetic does NOT close and no explanation is adopted here.

THIS IS THE COUNT_DISCIPLINE SHAPE EXACTLY: two correct sums over different
sets, wearing the same noun. The lesson from 2026-08-25 was that such numbers
are not guesses, they are correct answers to unasked questions -- and the fix
is to apply the discriminator, not to pick the one that looks right.

Settle it before either number reaches a published surface:

    git grep -l "@dottalk.usage" -- "*.cpp" "*.hpp" "*.h" | Measure-Object -Line
    git grep -l "@dottalk.usage.voluntary" -- "*.cpp" "*.hpp" "*.h" | Measure-Object -Line
    git grep -l "@dottalk.usage v1" -- "*.cpp" "*.hpp" "*.h" | Measure-Object -Line

If `source_census` matches the bare prefix and `contract_inventory` matches the
versioned marker, the difference is the voluntary set plus whatever else the
prefix sweeps up -- and one of the two tools should say which it counts.
