# Portal search map -- go straight there, do not scan (portal doctrine)

**Status:** maintained navigation index. Owner: member.derald. Date 2026-08-08. Registered as
recall node `doc.search_map`; reached from `trigger.where_is` and `trigger.onboard`.

## Why this exists

Broad `find` / `grep` over the tree is slow (worse across the mount -- it times out) and wasteful.
It is the thesis's binding constraint in disguise: "a memory that cannot be reached is,
functionally, a memory that does not exist" (5.1). The recall graph already fixes this for
doctrine; this map extends it to **code and registry targets** an agent commonly needs. Navigate
by pointer, not by scan.

Pointers are **file + symbol/section** (durable), not raw line numbers (perishable, AIF-082). A
`~Lnn` hint may be given, but trust the symbol and re-measure the line.

## The maintenance rule (the anti-scan discipline)

**When you had to do a broad grep/find to locate something, add a row here.** That is the search
analog of "synapse it": the target that just cost you a scan becomes a one-hop crosslink for the
next agent. A scan you did not record is a scan the next agent repeats.

## How to use instead of grep

1. Resolve by intent first: `python3 labtalk/ai_portal/recall.py <trigger>` returns the smallest
   working set, measured. `trigger.where_is` surfaces this map.
2. If the target is in the table, open the named file at the named symbol -- do not scan.
3. Only grep when the target is NOT here, and then **add a row** so the next agent does not.

| Which flavor a table was created as, and why the schema does not say | **A CREATE-TIME ARGUMENT THAT THE SCHEMA CONSTRAINS -- NOT A SCHEMA PROPERTY, AND IT SHOULD NOT BECOME ONE.** `DDL CREATE DBF X64 <t> FROM <schema>` vs `DDL CREATE DBF <t> FROM <schema>`: see `dottalkpp/data/scripts/ddl/ddl_schema_flavor_regression.dts` lines 12 and 22. **WHY THE TWO REGRESSION SCHEMAS DIFFER AT ALL** -- every difference is a CAPABILITY the classic flavor cannot express, not drift: field names of 15-18 chars (`student_identifier`) where a legacy descriptor's 10 bytes ARE the name; types `I`/`B`/`Y`/`T` (**VFP and X64, not x64-exclusive** -- `dbf_create.cpp type_allowed_for_flavor`, MSDOS gets C/N/F/D/L/M); UTF-8 vs CP437; ISO vs FOX dates; CDX vs CNX. So a classic-only schema creates either way, and an x64-featured schema creates ONLY as X64. **THE IMPLICATION IS ONE-WAY AND ENFORCED, NOT TRUNCATED:** `FIELDMGR APPEND: field name exceeds 10 characters (legacy flavor; long names require an x64 table)` and `field length >255 is only supported for X64 tables`. (The `~n` mangle seen in physical names such as `LOCALIZE~1` is NOT classic corruption -- it is x64's own projection of a long logical name onto the 10-char physical descriptor, which is why the reader's real-descriptor test is "name begins with a letter".) **THEREFORE DO NOT ADD A `flavor` FIELD TO THE SCHEMA JSONs.** It would be a SECOND AUTHORITY that can drift out of step with the field list, while the field list cannot disagree with itself -- the same failure `check-version-coherence` exists to prevent (one authority, no second declaration). The absence is correct; only the REASON was unwritten, which is what this row is. **WHAT IS GENUINELY UNRECORDED:** nothing outside the file stores which flavor a given LIVE table was created as -- byte 0 is the only witness. | `dottalkpp/data/scripts/ddl/ddl_schema_flavor_regression.dts` (which names both schema files); `src/xbase/fields_mgr.cpp` (refusals); `src/xbase/dbf_create.cpp` (`type_allowed_for_flavor`, `validate_lengths_for_flavor`). **THE TWO SCHEMA JSONs THIS SCRIPT CONSUMES ARE UNTRACKED** -- the regression is in the repository and its fixtures are not, so a fresh clone has the test and cannot run it.
