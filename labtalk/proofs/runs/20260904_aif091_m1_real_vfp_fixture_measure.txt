AIF-091 M1 -- REAL VFP OUTPUT DISAGREES WITH BYTE 23
captured 2026-09-04, D:\code\ccode, branch development, after dfd7cf15e

The commit dfd7cf15e claimed: 'every VFP- and x64-flavor table in this
repository carries ZERO at byte 18 AND ZERO at byte 23 (measured, 21 tables)'.
That measurement globbed *.dbf. Visual FoxPro does not name all of its tables
.dbf -- an .SCX is a form, a .VCX a class library, both DBF-format tables.

Re-measured by enumerating git ls-files (5,846 tracked paths) and selecting
files by MAGIC BYTE rather than extension:

READING:

  OBJCODE is the memo holding compiled object code in a VFP form or class
  library. VFP marks it BINARY (0x04 at byte 18) deliberately, so that no
  codepage translation is ever applied to compiled code. Byte 23 is 0x00.

    OLD code: flags = byte 23 = 0x00  ->  binary = FALSE   WRONG
    NEW code: flags = byte 18 = 0x04  ->  binary = TRUE    RIGHT

  Seven tracked files, written by Visual FoxPro, on which the two layouts
  give opposite answers. They were in this repository the whole time and
  were excluded by a file-extension filter, not absent from the tree.

SCOPE, so this is not oversold: this is real-VFP evidence for the BINARY
bit only. No tracked file carries 0x02 at byte 18, so nullability and the
_NullFlags bitmap remain proven against hand-computed byte tables alone.
R1a -- a nullable table authored in VFP -- is still owed for that half.
