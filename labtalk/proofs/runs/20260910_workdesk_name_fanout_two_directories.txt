WHAT THIS RUN SETTLES, and it is a correction to a comment I wrote myself.

The first two cuts of this spec used `USE WDARM AGAIN` and expected WORKDESK's
name-fanout section to appear. It never did, and the code was right.
`USE ... AGAIN` is the ONE route that cannot double a name: cmd_use.cpp
resolves the alias before it touches the area (find_open_area_by_alias at :472,
derive_distinct_alias at :492), renames the second instance to WDARM2 and
announces the rename. Two handles, two NAMES. The fanout pass keys on
DbArea::name(), which IS the logical name, so on that path it can never fire.

Every other opener skips that arm. WORKSPACE OPEN <dir> dedupes on PATH and not
on name (cmd_workspace.cpp:1511); WORKSPACE ADD, WORKSPACE LOAD and both
schema-restore paths apply a saved alias verbatim; CREATE and AUTODBF take the
file stem straight from DbArea::open(). cmd_use.cpp is the only uniquifier in
the tree.

So the arm reproduces the TOPOLOGY, not merely the condition: two DIFFERENT
files sharing a basename, opened from two directories into two workspaces --
the shape first seen live as x64\BUILDING.dbf and x32\BUILDING.dbf. Forcing the
collision with an explicit ALIAS clause was available and was refused; a spec
adjusted to match what the code did stops meaning anything.

OBSERVED IN THE SAME RUN AND NOT CLAIMED BY ANY ARM: WDKA and WDKB each report
the SESSION roots rather than the directory they were opened from, while their
tables demonstrably came from R131A and R131B (the SELECT lines print the real
paths). That is OPENJOIN's stated uncovered item (a) -- R131 wants a workspace
to record the directory it was opened from, Q3, still unruled -- observed here
rather than argued. Nothing in this change touches it.
