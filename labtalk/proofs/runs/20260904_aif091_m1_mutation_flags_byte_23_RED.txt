mutation : include/xbase_vfp.hpp VfpField restored to the pre-fix layout, with
           `flags` back at BYTE 23 (the autoincrement STEP value) and the dBASE III
           `reserved1`/`workarea`/`reserved2` members reinstated. That is exactly
           what shipped until 2026-09-04.
verdict  : MUTANT A refuses to compile. MUTANT B (someone deletes the asserts) reds
           8 runtime expectations. Both correct.

WHERE THIS RAN: g++ 12 -std=c++20 in the Linux container with the mutant headers
shadowed on the include path; the repository was never modified. The GREEN reading
is MSVC on the maintainer's machine.

WHY TWO MUTANTS. The static_asserts are the primary guard and they stop the defect
at BUILD time -- but an assert is only a guard while it exists, and the realistic
way this defect returns is someone reordering the struct and deleting the asserts
that then "fail for no reason". Mutant B is that person. The runtime test catches
them anyway.

READ THE DECOY LINES, because they are the defect stated in one number.

The decoy descriptor puts 0x02 (can store null) at byte 18 and 0x04 (binary) at
byte 23. `flags reads byte 18 -- got 4, want 2` is the old code picking up the
BYTE 23 value. The field then decodes as binary-and-not-nullable when the format
says nullable-and-not-binary: not a near miss, an exact inversion.

WHAT DID NOT MOVE, and it is the reason this survived so long: the FLAG DECODE
block and the FLAVOR block stayed green in mutant B. The decoding logic was always
right. It was being handed the wrong byte.
