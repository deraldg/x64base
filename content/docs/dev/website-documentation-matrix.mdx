## Proof Rules

| Status | Meaning | Promotion Rule |
| --- | --- | --- |
| runtime-evidenced | Source and runtime output or screenshots show the behavior. | Can be described as current behavior with conservative wording. |
| source-evidenced | Source, headers, registries, or contracts show the behavior. | Can be documented as implemented/source-defined, but should avoid runtime claims until tested. |
| help-catalog-evidenced | HELP, CMDHELP, command catalog, or metadata lists the surface. | Can seed catalog pages, then requires source/runtime review. |
| generated-reviewed | A report, matrix, manual section, or diagram was generated and reviewed before publication. | Can be promoted to website/manual copy with provenance. |
| manual-reviewed | A manual or reference artifact passed its documented review and acceptance gate. | Can be published with its pinned source snapshot, counts, and regeneration boundary. |
| planned-or-in-progress | The lane is real planning or active development, but not complete. | Keep under development docs and avoid product-complete wording. |
| review-needed | A scanner, memory note, or draft found something not yet verified. | Do not promote as a stable website claim. |

## Maintenance Classes

| Class | Rule |
| --- | --- |
| `static` | Deliberate website-owned copy; human review only. |
| `maintained` | Hand-authored page that tracks a named subject; review when that subject changes. |
| `maintained_current` | Permanent route with a replaceable present-state region; expose `as_of_date`, evidence state, and next gate while preserving event history. |
| `derived` | Regenerate or review when its source evidence changes. |
| `generated` | Regenerate from its authority; do not hand-edit generated regions. |
| `reported` | Append-only measurement or checkpoint with pinned provenance. |

## Direction Gates

| Flow | Gate | Website / Manual Rule |
| --- | --- | --- |
| implementation checkout -> website | Simplex default | Most website data should be derived, harvested, calculated, or reviewed from source/runtime/HELP/metadata/SelfDoc/manualgen evidence. |
| implementation checkout -> manual | Simplex default | Manuals should consume the same upstream evidence rather than copying website prose. |
| manual -> website | Duplex reviewed | Reviewed manual sections may feed website summaries when proof labels and source anchors are preserved. |
| website -> manual | Blocked default | The manual should not consume from the website unless the website artifact is not derivable elsewhere and is maintained separately. |
| website-owned artifact -> manual | Exception | Allowed for curated screenshots, public-only media, branding, hosted-download metadata, or contact/navigation artifacts with provenance. |

## Matrix Authority: Website Design and Retention

This matrix is not only a page-classification table. It is the authority of record
for two website policies: **design** (how pages are structured and what each must
carry) and **retention** (what must be preserved and how). A design or retention
decision that is not reflected here is not yet policy. Both route through the same
entry/closeout gate as any other website change: read the matrix before the pass,
re-audit it at signoff.

### Design authority

- **Page structure follows maintenance class.** The class decides how a page may be
  edited and what it must expose: `maintained_current` carries a present-state
  region with `as_of_date`, evidence state, and next gate; `generated` / `derived`
  regions are produced by their authority and never hand-shaped.
- **Evidence before ornament.** Every page must answer the Proofed Site Checklist
  below. Design may frame and organize evidence; it must not manufacture technical
  truth or hide the proof level.
- **Diagrams.** Conceptual/architectural diagrams are hand-authored `maintained` and
  kept in sync; data-carrying diagrams are `generated` from the harvest (AIF-032).
  Source and generated image are kept together.
- **Naming and routes.** Visible titles, nav labels, and prose use `DotTalk++`;
  short route buckets may stay stable for continuity but are not the public brand.
- New page types, hero/diagram placement conventions, and nav/section changes are
  design decisions and must be classified and recorded here when adopted.
- **Image assets must be license-clean and watermark-free before publish.** A
  website-owned image is only publishable with a clear license and no stock
  watermark. **Open for the next push (v5):** `public/images/talk-family/arctic-fox.png`
  (the Arctic mascot) may carry a faint stock watermark -- verify its license and
  replace it with a clean copy at the same path before or during the v5 flush.
  Also open for v5: `public/images/story/x64base-glass-engine.png` (origin-story
  figure) has embedded number plaques that conflict and read as noise -- photoshop
  or Firefly them out (content-aware / generative remove; the in-environment image
  tools cannot do object removal), keeping the same path.

### Retention authority

The website preserves history rather than overwriting it. The retention rule for a
page or artifact is set by its class and by these gates:

- **`maintained_current` -- preserve event history.** The present-state region is
  replaceable, but prior events and dates are retained, not erased.
- **`reported` -- append-only.** Measurements and checkpoints are appended with
  pinned provenance; a new run adds evidence, it does not replace the baseline.
- **README / orientation artifacts -- versioned.** Preserve the prior version before
  replacing it; README history is project provenance.
- **Historical source lineage -- byte-preserved.** SHA-256-bound, read-only, private
  roots omitted; checksums and truth-level labels retained.
- **Diagram sources retained with images.** Never discard the `.mmd` / `.drawio`
  source when publishing a generated image.
- **Publication checkpoints -- pinned.** Accepted manual/reference snapshots and the
  commits that served them are recorded and kept recoverable.

Retention is enforced at closeout: the matrix re-audit confirms that nothing which
should have been preserved was overwritten during the pass.

## Publication Matrix Check

Before source push or deployment, run the governed matrix checker from the
ccode authority tree against this website source tree. It is a hard publication
gate, not an advisory report.

The checker requires all of these relationships to pass together:

1. every MDX route is classified exactly once;
2. the full-stack publication entry passes, including engine -> canonical HELP
   build/store order and HELP/META producer freshness;
3. the command and function catalogs match current source;
4. error-code rows match current source; and
5. locale rows match current source; and
6. the FAQ has an `UPDATED` or `NO_CHANGE` matrix disposition and a review date
   matching the documentation-progress authority.

Today the second relationship uses a roughly one-second timestamp check because
the HELP store does not yet carry a content-addressed producer fingerprint. That
fallback conservatively treats a later engine recompile as E2-open. It is cheap
to run but can require an unnecessary HELP rebuild after an unrelated code
change. The gold refinement is to stamp the HELP build with a digest of the
catalogs, extracted HELP contracts, and HELP generator implementation, then
compare that digest here. Until that provenance exists, publication fails
closed even when the website itself builds successfully.

## Proofed Site Checklist

A website page is proofed when the page can answer four questions:

1. What source or document lane fed this page?
2. What proof level is being claimed?
3. What artifact, command, report, screenshot, or source path backs it?
4. What needs to be regenerated when the underlying command, function, or lane changes?

The site currently meets this standard best for engine feature crosswalks,
data mutators, x64 capacity math, runtime evidence, historical source lineage,
and the SelfDoc publication pages. The accepted manual/reference checkpoint is
now public in site source; the weaker area remains the fully automated
regeneration loop, which is documented as partial rather than complete.
